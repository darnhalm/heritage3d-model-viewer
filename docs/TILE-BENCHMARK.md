# Пассивный benchmark тайлизации

## Зачем он нужен

Основной production-набор сравнивает четыре доступных порядка загрузки 3D Tiles на одной
сцене Kronstadt и одном воспроизводимом маршруте камеры. Отдельные наборы `formats` и `full`
оставлены для диагностики разных форматов. Стенд измеряет фактическое поведение загрузчика и
LOD, не опираясь на визуальное впечатление:

- время до первого видимого содержимого и первого изменения LOD;
- время окончания активной подкачки;
- выбранные уровни, число переходов и возвратов к более грубому уровню;
- очередь, параллельные загрузки, запросы, повторные запросы и переданные байты;
- размер кэша GLB, активные сплаты, давление на SSE и JS heap;
- CPU-время `app.tick` (p50/p95/p99);
- контрольные снимки в одинаковых точках маршрута.

## Почему benchmark не влияет на плеер

В `src/` нет benchmark-кода, URL-параметра или дополнительного UI. Внешний Playwright-скрипт
открывает обычный viewer и дополнительно прокручивает его одинаковыми временными шагами — это
нужно для headless Chromium, где цикл с `autoRender=false` может останавливаться.
Он намеренно держит `debug.tileRecording=false`: тайлы не закрепляются в кэше, поэтому
вытеснение, повторные загрузки и реакция на лимит памяти остаются естественными.

Для загрузки используется существующий `viewer.loadFiles`, а для чтения — существующие
read-only статистика и состояние менеджеров. Скрипт не меняет алгоритмы LOD, приоритеты
очереди или лимиты памяти.

## Запуск локально

Полный локальный набор использует сцены, которые уже лежат в `dist/models`:

```bash
BENCH_TILE_SUITE=full npm run benchmark:tiles
```

Короткая проверка генератора отчёта:

```bash
BENCH_TILE_SUITE=smoke \
BENCH_TILE_PASSES=cold \
BENCH_STEP_MS=250 \
BENCH_SETTLE_MS=1000 \
BENCH_SCREENSHOTS=0 \
npm run benchmark:tiles
```

Полезные переменные:

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `BENCH_URL` | `http://127.0.0.1:4173/` | Viewer, который проверяется |
| `BENCH_TILE_SUITE` | `production` | `production`, `formats`, `full` или `smoke` |
| `BENCH_TILE_SCENES` | — | Список ID сцен через запятую вместо suite |
| `BENCH_TILE_VARIANTS` | — | Список ID режимов через запятую вместо всех вариантов сцены |
| `BENCH_TILE_PASSES` | `cold,warm` | Холодный либо холодный + прогретый HTTP-кэш |
| `BENCH_NETWORK` | `native` | `native`, `broadband` или `fast3g` |
| `BENCH_RUNS` | `1` | Число повторов каждого варианта |
| `BENCH_STEP_MS` | `2500` | Время в каждой точке маршрута |
| `BENCH_SAMPLE_MS` | `100` | Период чтения статистики |
| `BENCH_STARTUP_MS` | `90000` | Таймаут появления первого содержимого |
| `BENCH_SETTLE_MS` | `10000` | Максимальное ожидание спокойной очереди |
| `BENCH_SCREENSHOTS` | `1` | Сохранять контрольные изображения |
| `BENCH_OUTPUT` | `benchmark-results` | Корневой каталог результатов |

Каждый прогон создаёт отдельный timestamp-каталог:

- `results.json` — полные данные;
- `summary.csv` — одна строка на сцену/вариант/кэш;
- `samples.csv` — временной ряд;
- `report.md` — компактная таблица;
- `report.html` — автономный отчёт с графиками;
- `screenshots/` — точки маршрута, если включены.

## GitHub Actions и защита

Workflow `Benchmark tile streaming` запускается только вручную через `workflow_dispatch`.
Запустить его в основном репозитории могут только пользователи с правом записи. Публичного
benchmark-режима в viewer нет, поэтому посетитель production не может включить сбор данных.

Репозиторий публичный, следовательно артефакты Actions нельзя считать секретным хранилищем.
Поэтому workflow принимает только заранее заданные варианты, работает с публичными сценами и
сохраняет только обезличенные технические показатели. Query string, cookies, заголовки и
содержимое моделей в отчёт не попадают. Для приватных сцен стенд следует запускать локально;
их адреса и результаты нельзя загружать в этот workflow.

## Как читать сравнение

Варианты одной сцены сравниваются напрямую. Kronstadt запускается во всех четырёх режимах:
`error + distance`, `center first`, `cursor first` и `surface point first` — на одном маршруте
и сетевом профиле.

Для курсорного режима маршрут содержит фиксированные нормализованные координаты указателя.
Для surface-режима скрипт сначала использует быстрый mesh-pick. Если CPU-геометрия недоступна,
используется направление к bounding volume ближайшего видимого тайла: алгоритм приоритета
использует только направление, а не глубину точки. GPU depth-pick остаётся последним fallback,
но его цена не попадает в обычный surface-прогон и не искажает сравнение загрузчиков. При промахе скрипт пробует точку
на полпути к центру и затем центр. В `samples.csv` сохраняется конкретный `focusSource`. Поле
`exactFocusPercent` в JSON/CSV и `Focus active` в отчёте считают измеряемый маршрут после
появления первого содержимого и подтверждают, что режим действительно получил нужный сигнал. Если
surface-точка ни разу не найдена, вариант считается пропущенным, а не выдаётся за корректное
сравнение.

Строки разных исходных сцен — например Kronstadt GLB и JUMA GSplat — показывают поведение
форматов и загрузчиков, но не являются сравнением качества геометрии. Для научно корректного
сравнения разных упаковок нужен один исходник, преобразованный всеми проверяемыми конвейерами;
для этого в конфигурации есть группа вариантов Armour.

`fallbackCount` учитывает только падения глубины внутри одной неподвижной точки маршрута.
Намеренное отдаление камеры между точками возвратом к грубому LOD не считается.

## Паспорт машины и время кадра

Отчёт начинается строкой о машине: видеокарта (`WEBGL_debug_renderer_info` — строка приходит на
любом бэкенде), бэкенд, процессор и размер буфера кадра в пикселях. Без неё два прогона с разных
машин несопоставимы, а цифры выглядят абсолютными, хотя таковыми не являются.

Строка сразу показывает и подмену: в headless-браузере Chromium обычно берёт SwiftShader, то есть
рисует процессором. В таком прогоне GPU-время идёт сотнями миллисекунд и про настоящую видеокарту
не говорит ничего — сравнивать его с прогоном на живой машине нельзя.

К каждому результату добавлены `gpuFrameP50Ms`, `gpuFrameP95Ms`, `cpuFrameP50Ms`, `vramTotalMb` и
`vramTexturesMb`. Оговорки:

- **GPU-время** берётся у профилировщика движка (`gpuProfiler._frameTime`) и есть не везде: там,
  где метки времени недоступны, поле остаётся пустым. Разбивки по проходам нет — только кадр целиком.
- **Видеопамять** — учёт движка: сколько он сам выделил под текстуры и буферы. Сколько на самом деле
  держит драйвер, браузер не сообщает, и эти числа не совпадают.
- **CPU-время кадра** меряется от `frameupdate` до `frameend`, то есть работа главного потока,
  включая наши оверлеи; ожидание вертикальной синхронизации в него не входит.

Сетевой размер источников и внутренний размер GLB-кэша остаются, как и раньше, самыми
воспроизводимыми числами отчёта: они не зависят ни от машины, ни от драйвера.

## 3TZ против отдельных файлов

Отдельный A/B на одной и той же сцене Kronstadt в Yandex Object Storage зафиксирован в
[решении по публикации 3D Tiles и использованию 3TZ](api/3TZ-PUBLICATION-DECISION-RU.md).
Краткий итог: 3TZ остаётся единым форматом загрузки и архивирования, но production-плеер получает
распакованный `tileset.json` и отдельные тайлы ради первого кадра, параллельной загрузки и
нормального warm-кэша. Агрегированные машинные данные лежат в
[`experiments/3tz-vs-files-yandex-2026-10-27.json`](experiments/3tz-vs-files-yandex-2026-10-27.json).
