# Решение по публикации 3D Tiles и использованию 3TZ

**Дата:** 27 октября 2026 года
**Статус:** принято для целевой архитектуры; серверная распаковка и публикация ещё должны быть реализованы
**Область:** загрузка, хранение, публикация и онлайн-просмотр наборов 3D Tiles

## Решение

3TZ используется как единый входной и архивный файл, но не как основной production-формат
стриминга в браузер.

Целевой поток:

```text
пользователь загружает один .3tz
                 │
                 ▼
сервер проверяет архив, структуру и лимиты
                 │
                 ▼
сервер публикует неизменяемую версию пакета
tileset.json + отдельные GLB/B3DM/текстуры/subtree
                 │
                 ▼
плеер загружает tileset.json и необходимые тайлы через CDN
```

Оригинальный 3TZ можно сохранять как исходник, резервную копию и формат скачивания. Плеер
продолжает поддерживать прямое открытие локальных и удалённых 3TZ, но публичный manifest по
умолчанию должен указывать на распакованный `tileset.json`.

Поддержка обычного `tileset.json` и отдельных ресурсов из плеера не удаляется.

## Почему выбран этот вариант

Один 3TZ удобен на границе системы:

- пользователь загружает один файл вместо каталога с тысячами объектов;
- пакет можно проверить и зарегистрировать атомарно;
- исключаются потерянные GLB, текстуры, subtree и внешние tileset;
- проще хранить исходник, контрольную сумму и версию конвертации;
- для скачивания и переноса модели достаточно одного объекта.

Отдельные ресурсы эффективнее на пути от CDN к браузеру:

- каждый тайл кешируется независимо;
- браузер повторно использует уже загруженные тайлы;
- HTTP/2 и HTTP/3 позволяют параллельно загружать множество ресурсов;
- изменение версии не требует специальных правил кеширования диапазонов одного большого файла;
- ошибка или повреждение одного объекта не превращает весь набор в недоступный архив;
- проще наблюдать запросы, размеры и ошибки отдельных тайлов.

## A/B-замер на Yandex Object Storage

Для проверки использовалась одна и та же опубликованная сцена Kronstadt:

- исходный набор: 4 748 файлов, 254 022 573 байта;
- эквивалентный 3TZ: 4 749 записей, 254 675 137 байт;
- 3TZ собран официальным `3d-tiles-tools`, без повторного ZIP-сжатия, со стандартным
  `@3dtilesIndex1@`;
- обе версии читались из одного бакета Yandex Object Storage;
- Yandex корректно отвечал `206 Partial Content`, `Accept-Ranges: bytes` и не применял
  `Content-Encoding` к архиву;
- использовались текущая сборка плеера, одинаковый viewport, один маршрут из шести положений
  камеры и три повтора cold/warm;
- измерение выполнялось Chrome с рабочей станции в Costa Rica до Yandex `ru-central1`.

Медианы трёх прогонов:

| Метрика | Отдельные файлы | 3TZ |
|---|---:|---:|
| Первый видимый тайл, cold | **1,76 с** | 3,39 с |
| Стабилизация очереди, cold | **13,14 с** | 26,56 с |
| Запросы модели, cold | 229 | **124** |
| Передано по сети, cold | 21,57 МБ | **5,88 МБ** |
| Первый видимый тайл, warm | **0,37 с** | 2,96 с |
| Стабилизация очереди, warm | **10,74 с** | 25,11 с |
| Передано по сети, warm | **0,65 МБ** | 6,39 МБ |

3TZ сократил число запросов и холодный сетевой трафик, но текущий загрузчик позже показал
первый тайл и медленнее стабилизировал LOD. При повторном открытии отдельные ресурсы почти
полностью пришли из браузерного кеша. Диапазоны `206` одного 3TZ в проверенной связке
Chrome + Yandex Object Storage повторно по HTTP-кешу не использовались.

Экономия трафика 3TZ не означает одинаковое качество в каждый момент теста: загрузчик архива
держал меньшую очередь и менее агрессивно подкачивал следующий LOD. Поэтому главным критерием
решения остаются время до первого видимого содержимого, стабилизация и поведение warm-кеша, а
не только сумма байтов.

Агрегированные результаты сохранены в
[`../experiments/3tz-vs-files-yandex-2026-10-27.json`](../experiments/3tz-vs-files-yandex-2026-10-27.json).

### Ограничения замера

Это вывод для текущего плеера, Chrome и Yandex Object Storage, а не универсальное свойство
формата 3TZ. Высокая межрегиональная задержка усиливает цену последовательных Range-запросов.
Перед существенной сменой CDN, загрузчика или географии пользователей тест необходимо повторить
с той же исходной сценой минимум из `ru-central1` и ещё одного целевого региона.

### Оптимизация загрузчика от 27 октября 2026 года

`ThreeTzResourceProvider` больше не строит карту всего архива через
`ZipReader.getEntries()` в основном пути. Новый reader:

1. читает EOCD и только последнюю запись ZIP Central Directory;
2. проверяет, что последняя запись — несжатый `@3dtilesIndex1@`;
3. загружает индекс и ищет путь бинарным поиском по MD5;
4. проверяет совпадение имени в Local File Header и CRC данных;
5. читает только выбранную запись, а не весь каталог;
6. объединяет чтение в выровненные блоки по 256 КиБ и хранит LRU-кеш до 16 МиБ;
7. при некорректном или старом архиве возвращается к совместимому
   `ZipReader.getEntries()`.

Это соответствует рекомендации
[спецификации 3TZ](https://github.com/Maxar-Public/3tz-specification/blob/main/Specification.md)
использовать индекс для случайного доступа, а не универсальный ZIP reader. Поддержаны ZIP/ZIP64,
Store и Deflate; зашифрованные записи и выходы за границы файла отклоняются.

Контрольный повтор на том же 243-МиБ архиве показал:

| Метрика 3TZ | Индекс без блочного кеша | Индекс + блочный кеш |
|---|---:|---:|
| Range-запросы, cold | 90 | **32** |
| Range-запросы, warm | 92 | **32** |
| Ответы до первого видимого тайла, cold | 12 | **3** |
| Логический объём выбранных диапазонов, cold | **7,33 МиБ** | 8,88 МиБ |
| Range-ответы из browser cache, warm | 0 из 92 | **медиана 31 из 32** |

Таким образом, блочный кеш сократил число Range-запросов примерно на 64% и сделал диапазоны
стабильными между открытиями. В двух warm-прогонах почти все ответы пришли из browser cache
(`Resource Timing transferSize = 0`), однако в третьем кешировались только 7 из 32 ответов.
Следовательно, переиспользование Range-кеша улучшилось, но пока не гарантировано. Цена — примерно
1,55 МиБ дополнительного чтения в cold-прогоне из-за выравнивания диапазонов.

Абсолютное время контрольного повтора не используется для пересмотра решения: во время второй
серии межрегиональная сеть заметно деградировала (cold time-to-first-visible имел разброс
1,88–10,56 с). Устойчивыми сигналами здесь являются число и форма Range-запросов и попадание
повторных диапазонов в кеш. Для сравнения времени нужен отдельный запуск из `ru-central1` или
одновременный A/B из одного клиента.

## Безопасность

3TZ не является границей безопасности, шифрованием или DRM. Пользователь, которому разрешён
просмотр, получает байты модели и может сохранить как отдельные тайлы, так и весь 3TZ. Более того,
единый архив упрощает массовое скачивание модели после получения URL.

Безопасность должна обеспечиваться независимо от представления:

- приватный bucket или закрытый origin;
- авторизация через session gateway, CDN-cookie либо короткоживущие signed URL;
- неизменяемые версии публикаций и непредсказуемые внутренние идентификаторы;
- отсутствие секретов и долгоживущих токенов в manifest и постоянных URL;
- журналирование выдачи и скачивания;
- отдельные правила для публичных демонстрационных и приватных пользовательских моделей.

На дату замера бакет `playcanvasviewer` имел:

```text
anonymous read: true
anonymous list: true
```

Публичный листинг возвращал все 7 621 ключ бакета. Это отдельный риск конфигурации, который не
исправляется переходом на 3TZ. Для публичных демонстрационных ассетов допустимо оставить
анонимное чтение, но анонимный `list` следует отключить. Приватные пользовательские модели не
должны находиться под анонимным `read`.

## Проверка входного 3TZ

Сервер не должен распаковывать пользовательский архив непосредственно в production-префикс.
До публикации необходимо:

1. Проверить расширение, MIME, сигнатуру ZIP/3TZ и контрольную сумму загрузки.
2. Проверить наличие корректных `tileset.json` и `@3dtilesIndex1@`.
3. Отклонить абсолютные пути, `..`, повторяющиеся имена, симлинки и вложенные 3TZ.
4. Ограничить количество записей, размер одной записи, общий распакованный объём и коэффициент
   сжатия, чтобы исключить ZIP bomb и исчерпание памяти/диска.
5. Проверить, что все относительные ссылки tileset разрешаются внутри пакета.
6. Проверить допустимые типы контента и базовую структуру GLB/B3DM/subtree.
7. Распаковать в изолированную временную область.
8. Опубликовать новую неизменяемую версию атомарно и только после успешной проверки.

Отказ на любом этапе оставляет предыдущую опубликованную версию активной.

## Контракт хранения и публикации

Для одного загруженного ассета сервер хранит два разных представления:

| Представление | Назначение | Доступ |
|---|---|---|
| Исходный `.3tz` | архив, повторная обработка, скачивание | приватный; временный download URL |
| Распакованная производная | онлайн-просмотр и CDN-кеш | manifest/session gateway или публичный CDN для открытых моделей |

Производная должна содержать:

- `rootPath: tileset.json`;
- версию конвертера и профиля обработки;
- общий размер и количество объектов;
- контрольные суммы или ETag инвентаря;
- неизменяемый version prefix;
- статус проверки и публикации.

Рекомендуемая последовательность состояний:

```text
uploaded → validating → unpacking → publishing → ready
                                      └────────→ failed
```

Публичный manifest возвращает URL корневого `tileset.json`, а download endpoint — временный URL
исходного 3TZ. Эти адреса не должны подменять друг друга.

## Когда решение можно пересмотреть

3TZ может стать основным онлайн-представлением только после повторного benchmark, если выполнены
все условия:

- загрузчик использует `@3dtilesIndex1@` напрямую;
- Range-запросы объединяются и не сериализуют независимые тайлы;
- реализован проверенный кеш диапазонов либо CDN/browser действительно повторно использует их;
- исключена возможность ответа `200` со всем архивом вместо ожидаемого `206`;
- время первого видимого тайла не хуже отдельных файлов более чем на 10%;
- warm-повтор не требует повторной передачи уже просмотренных тайлов;
- тесты пройдены минимум на крупной explicit-сцене, implicit tiling и нескольких целевых регионах;
- сохранены авторизация, отзыв доступа и наблюдаемость запросов.

До выполнения этих критериев 3TZ-only для production-плеера не принимается.
