# Тайлизация GLB в PlayCanvas Model Viewer

Статус: концепция для обсуждения, без реализации.

## Задача

Добавить в текущий PlayCanvas Model Viewer потоковый показ больших glTF/GLB-сцен:
вместо загрузки одного монолитного GLB вьюер получает небольшое дерево GLB-тайлов,
показывает подходящий уровень детализации и выгружает невидимые данные.

Цель — ограничить:

- время до первого содержательного кадра;
- объём одновременно занятой CPU/GPU-памяти;
- число видимых треугольников и draw calls;
- сетевой трафик при перемещении камеры.

Общий размер набора данных при этом может быть намного больше доступной памяти браузера.

## Текущий контекст

Этот репозиторий уже построен на PlayCanvas. Текущая загрузка glTF находится в
`src/viewer.ts`: модель создаётся как `container` asset, а сцена — через
`instantiateRenderEntity()`. Там же рассчитываются `sceneBounds` и
`dynamicSceneBounds`.

Переданный отдельно минифицированный `app.js` использует Three.js, `GLTFLoader` и
`TilesRenderer`. Его полезно рассматривать как референс поведения:

- иерархический выбор тайлов;
- frustum culling;
- оценка экранной ошибки;
- загрузка и выгрузка контента;
- обновление набора тайлов при движении камеры.

Код Three.js переносить напрямую не нужно. Менеджер тайлов должен использовать нативные
Asset, Entity, Render Component, BoundingBox и Frustum API PlayCanvas.

## Главный принцип

Тайлизация выполняется **до открытия модели во вьюере**:

```text
исходный GLB
    ↓
офлайн-конвертер
    ↓
tileset.json + GLB-тайлы нескольких LOD
    ↓
Object Storage / CDN
    ↓
PlayCanvas TileManager
```

Делить большой GLB в браузере не планируется. Это потребовало бы сначала скачать и
распаковать всю модель, то есть не решило бы основную проблему.

## Предлагаемый формат

На первом этапе стоит поддержать небольшой практический поднабор формата 3D Tiles:

- `asset.version`;
- `root`;
- `boundingVolume.box` и затем `boundingVolume.sphere`;
- `geometricError`;
- `refine: "REPLACE"`; позже — `"ADD"`;
- `content.uri`;
- `children`;
- `transform`.

Контентом тайла будет обычный `.glb`, без обязательного контейнера `.b3dm`.

Пример:

```json
{
  "asset": {
    "version": "1.1",
    "generator": "heritage3d-glb-tiler"
  },
  "geometricError": 24,
  "root": {
    "boundingVolume": {
      "box": [0, 4, 0, 20, 0, 0, 0, 8, 0, 0, 0, 20]
    },
    "geometricError": 12,
    "refine": "REPLACE",
    "content": {
      "uri": "tiles/root.glb"
    },
    "children": []
  }
}
```

Совместимость с базовой структурой 3D Tiles позволит:

- проверять наборы сторонними инструментами;
- использовать уже существующие тайлсеты, если их расширения укладываются в выбранный
  поднабор;
- не изобретать собственную схему для bounds, transforms, LOD и refinement.

Полную поддержку спецификации 3D Tiles в MVP закладывать не нужно. В частности, можно
отложить implicit tiling, multiple contents, metadata, внешние tileset JSON и специальные
контейнеры контента.

## Офлайн-тайлизатор

### 1. Нормализация исходной модели

Перед разбиением нужно:

- применить или корректно сохранить transform узлов;
- привести геометрию к одной согласованной системе координат;
- вычислить world-space bounds;
- сохранить материалы, UV, normals, tangents и vertex colors;
- определить единицы модели, не меняя их без явной настройки;
- проверить анимации, skinning и morph targets.

Первая версия может официально поддерживать только статическую геометрию. Разбиение
анимированных и skinned-моделей по пространству существенно сложнее.

### 2. Пространственное дерево

Базовый вариант — octree:

- корень содержит bounds всей сцены;
- узел делится на восемь дочерних областей;
- деление продолжается, пока не выполнены бюджеты тайла;
- слишком пустые или мелкие ветви не создаются.

Для преимущественно плоских объектов можно позднее добавить quadtree или адаптивное BVH.
Для MVP octree проще и достаточно универсален.

Предварительные целевые бюджеты одного листового тайла:

| Параметр | Стартовое значение |
|---|---:|
| Треугольники | 50–200 тыс. |
| Несжатый GPU-объём | 10–40 МБ |
| Размер GLB по сети | 1–10 МБ |
| Материалы / draw calls | желательно до 10–30 |

Это настройки конвертера, а не жёсткие ограничения формата.

### 3. Геометрия на границах

Меши, пересекающие несколько областей, — ключевой вопрос тайлизатора.

Возможные стратегии:

1. Назначать целый mesh по центру bounds. Просто, но крупный mesh может разрушить
   пространственное разбиение.
2. Дублировать mesh в пересекающихся тайлах. Просто в runtime, но увеличивает размер и
   может давать наложение геометрии.
3. Разрезать геометрию по треугольникам и пересобрать vertex/index buffers. Это основной
   кандидат для статических heritage/scan-моделей.
4. Сначала разделять по существующим объектам, а слишком крупные объекты дополнительно
   резать по треугольникам. Это наиболее практичный гибрид.

Для MVP предлагается гибридный вариант №4. Треугольник не нужно физически обрезать
плоскостью тайла: достаточно целиком назначить его области по центроиду. Это может немного
расширить фактические bounds тайла, поэтому bounds следует вычислять после разбиения по
реальной геометрии, а не брать геометрическую ячейку octree.

### 4. Уровни детализации

При `REPLACE` родитель содержит упрощённое представление всего поддерева, а дети —
более детальную геометрию.

Возможная цепочка:

```text
LOD 0: очень грубая модель всей сцены
LOD 1: крупные регионы
LOD 2: средние регионы
LOD 3: детальные листовые тайлы
```

Для каждого узла сохраняются:

- GLB его текущего представления;
- точный bounding volume;
- `geometricError`;
- ссылки на дочерние узлы.

Первый полезный кадр должен требовать скачивания только корневого или нескольких
верхнеуровневых GLB.

Упрощение геометрии должно по возможности:

- сохранять границы и UV-швы;
- не разрушать normals;
- учитывать материал;
- не создавать щели между соседними областями;
- иметь измеряемую ошибку, из которой можно получить `geometricError`.

### 5. Материалы и текстуры

Встраивание одинаковых текстур в каждый GLB проще, но быстро создаёт дубликаты. Возможные
этапы оптимизации:

1. MVP: самодостаточные GLB с embedded-текстурами.
2. KTX2/Basis для уменьшения сети и GPU-памяти.
3. Общие внешние текстуры, кэшируемые браузером.
4. Атласы по материалу или региону.

При сборке желательно объединять совместимые primitives с одинаковым материалом.
Для реального FPS это часто важнее дополнительного уменьшения числа треугольников.

### 6. Сжатие

Следует отдельно измерить:

- Meshopt: обычно удобен для потоковой доставки и быстрого декодирования;
- Draco: может дать меньший файл, но требует CPU-времени на декодирование;
- KTX2/Basis: основной кандидат для текстур.

Сжатый размер файла нельзя использовать как оценку памяти. Кэш должен учитывать хотя бы
приблизительный декодированный объём vertex/index buffers и текстур.

## Runtime в PlayCanvas

### Предлагаемые модули

```text
src/tiles/
├── tile-types.ts          типы tileset.json и runtime-состояния
├── tileset-loader.ts      загрузка и проверка JSON
├── tile-manager.ts        обход дерева и общий жизненный цикл
├── tile-selector.ts       frustum + SSE + refinement
├── tile-content.ts        PlayCanvas Asset/Entity для одного GLB
├── tile-request-queue.ts  приоритеты, лимиты, отмена
├── tile-cache.ts          LRU и бюджеты памяти
└── tile-debug.ts          bounds, LOD-цвета и статистика
```

На первом этапе модули можно интегрировать через `Viewer`, но не следует добавлять всю
логику прямо в уже крупный `src/viewer.ts`.

### Жизненный цикл тайла

```text
UNLOADED
    ↓ запрос
QUEUED
    ↓ началась загрузка
LOADING
    ↓ GLB создан
READY
    ↓ выбран для кадра
VISIBLE
    ↓ больше не нужен
READY
    ↓ вытеснен из кэша
UNLOADED
```

Дополнительно нужны состояния `FAILED` и, возможно, `ABORTED`.

`TileContent` должен владеть:

- PlayCanvas `Asset`;
- созданной `Entity`;
- оценкой CPU/GPU-памяти;
- временем последнего использования;
- безопасным `destroy/unload`, не затрагивающим ресурсы других тайлов.

Нужно отдельно проверить совместно используемые текстуры: нельзя уничтожить общий asset,
пока на него ссылается другой видимый тайл.

### Выбор LOD

Основная метрика — screen-space error:

```text
SSE = geometricError * viewportHeight
      / (distance * 2 * tan(verticalFov / 2))
```

Если SSE выше порога, узел нужно уточнять дочерними тайлами. Начальное значение порога
можно взять в диапазоне 8–24 пикселей и затем подобрать на реальных моделях.

При выборе учитываются:

- пересечение bounding volume с frustum камеры;
- расстояние до bounding volume, а не только до его центра;
- SSE;
- доступность дочернего контента;
- сетевой и memory budget;
- направление и скорость движения камеры.

Тайлы в центре экрана и ближайшие к камере получают больший приоритет загрузки.

### Переключение без дыр

Для `REPLACE` нельзя скрывать родителя, пока все необходимые дети не готовы. Безопасная
последовательность:

1. Родитель остаётся видимым.
2. Дети загружаются.
3. Когда нужный набор детей готов, дети показываются.
4. Родитель скрывается.

При обратном переходе сначала показывается готовый родитель, затем скрываются дети.

Небольшой hysteresis для порога SSE предотвратит постоянное переключение LOD на границе.
Короткий cross-fade можно добавить позже, если он не создаёт прозрачностных артефактов и
лишних draw calls.

### Очередь запросов

Начальные параметры:

| Параметр | Desktop | Mobile |
|---|---:|---:|
| Одновременные загрузки GLB | 6–8 | 3–4 |
| Одновременное декодирование | 2–4 | 1–2 |
| Предзагрузка соседних тайлов | ограниченная | выключена или минимальная |

Запрос нужно отменять или понижать в приоритете, если камера ушла из области до окончания
загрузки. Возможность настоящей отмены зависит от используемого пути PlayCanvas Asset API;
как минимум результат устаревшего запроса не должен автоматически становиться видимым.

### Кэш и память

Нужны два ограничения:

- максимальное число готовых невидимых тайлов;
- приблизительный лимит декодированной памяти.

Кандидаты для вытеснения:

1. невидимые;
2. давно не использованные;
3. далёкие от камеры;
4. имеющие готового родителя, который может их заменить.

Видимый тайл нельзя выгружать до появления допустимой замены.

Начальные ориентиры, которые обязательно уточняются профилированием:

| Платформа | Кэш декодированных тайлов |
|---|---:|
| Desktop | 512–1024 МБ |
| Mobile | 128–256 МБ |

Автоматический выбор профиля можно связать с типом устройства и доступной информацией о
памяти, но пользовательская настройка должна иметь приоритет.

## Бюджеты кадра

Для цели 60 FPS один кадр имеет 16,7 мс. Обход дерева не должен занимать заметную часть
этого бюджета, поэтому:

- обновлять selection каждый кадр только при движении камеры или изменении viewport;
- тяжёлые операции распределять по кадрам;
- не создавать и не уничтожать много Entity в одном кадре;
- заранее хранить bounds и не пересчитывать их по всей геометрии;
- ограничить число одновременно активируемых тайлов.

Предварительные ориентиры видимого набора:

| Платформа | Треугольники | Draw calls |
|---|---:|---:|
| Мощный desktop | 2–5 млн | 300–700 |
| Средний ноутбук | 1–3 млн | 200–500 |
| Современный телефон | 0,3–1 млн | 80–200 |

Это не обещание FPS, а стартовые рамки для тестов. Освещение, тени, overdraw, размер
текстур и количество материалов могут оказаться важнее числа треугольников.

## Интеграция с возможностями viewer

### Scene bounds и камера

Корневой bounding volume должен сразу задавать `sceneBounds`, не дожидаясь загрузки всех
GLB. Это позволит:

- корректно выполнить fit camera;
- настроить near/far;
- вычислить скорость камеры;
- настроить grid, shadow distance и dimension box.

`dynamicSceneBounds` для тайлсета не следует пересчитывать только по текущим видимым
тайлам: иначе bounds и связанные настройки будут прыгать при смене LOD.

### Picking, измерения и hotspots

Raycast должен выполняться только по видимым Render Components.

Нужно определить стабильность идентификаторов объектов между LOD:

- если идентификатор нужен только для визуального попадания, достаточно текущего mesh;
- если к объекту привязаны hotspot, измерение или внешние metadata, нужен стабильный ID,
  одинаковый или сопоставимый между уровнями детализации.

Для измерений предпочтительно попадать в самый детальный уже загруженный тайл. При
недостаточном LOD интерфейс может временно запросить уточнение области.

### Alignment и transform

Transform всего тайлсета должен применяться к одному корневому Entity. Локальные
`transform` узлов tileset применяются ниже него. Это позволит сохранить текущие
инструменты перемещения, вращения и масштаба модели без модификации каждого GLB.

### Загрузка URL

`.json` уже используется в интерфейсе для нескольких видов данных, поэтому tileset нужно
распознавать по структуре (`asset`, `root`, `geometricError`), а не только по расширению.

Относительные `content.uri` разрешаются относительно URL текущего `tileset.json`.
Object Storage/CDN должен возвращать корректный CORS и MIME type.

## Диагностика

Для разработки нужен debug overlay:

- FPS и CPU frame time;
- число выбранных, видимых, загружаемых и закэшированных тайлов;
- видимые треугольники и draw calls, насколько это доступно;
- сетевой объём;
- приблизительная память кэша;
- текущий SSE threshold;
- цветовая раскраска LOD;
- визуализация bounding boxes;
- причины выбора/отбрасывания тайла.

Без этой информации настройка тайлизатора и runtime превратится в угадывание.

## Ошибки и деградация

Runtime должен:

- оставлять родительский LOD при ошибке загрузки ребёнка;
- повторять временные сетевые ошибки с ограниченным backoff;
- не повторять бесконечно 404 и ошибки формата;
- показывать понятную ошибку, если не загрузился корень;
- продолжать работу при повреждении отдельной необязательной ветви;
- очищать частично созданные Assets и Entities после ошибки.

## Этапы реализации

### Этап 0. Набор тестовых данных

- один маленький ручной tileset;
- одна крупная реальная модель;
- модель с несколькими материалами и текстурами;
- намеренно повреждённый тайл для проверки деградации.

### Этап 1. Минимальный runtime

- чтение `tileset.json`;
- bounds корня;
- загрузка одного GLB;
- создание и уничтожение PlayCanvas Entity;
- общий transform тайлсета.

### Этап 2. Иерархия

- рекурсивное дерево;
- frustum culling;
- SSE;
- `REPLACE` без визуальных дыр;
- очередь запросов.

### Этап 3. Память и устойчивость

- LRU;
- лимиты памяти;
- отмена/игнорирование устаревших запросов;
- retry и обработка ошибок;
- debug overlay.

### Этап 4. Интеграция viewer

- камера и fit;
- picking;
- измерения;
- hotspots;
- alignment;
- экспорт/импорт настроек.

### Этап 5. Офлайн-конвертер

- octree;
- разбиение primitives;
- генерация LOD;
- упаковка материалов и текстур;
- валидация `tileset.json`;
- публикация в Object Storage.

Runtime целесообразно прототипировать раньше собственного конвертера на маленьком
тестовом tileset. Это разделит проблемы формата, рендера и генерации данных.

## Критерии успешного прототипа

- корневой LOD появляется без загрузки всей сцены;
- при приближении камера получает более детальные тайлы;
- при удалении детали освобождаются из кэша;
- переключение `REPLACE` не создаёт пустых областей;
- возврат камеры использует кэш без повторного скачивания;
- bounds и camera fit не меняются при переключении LOD;
- повреждение дочернего тайла не скрывает доступный родитель;
- на тестовой модели собираются метрики времени первого кадра, FPS, сети и памяти.

## Открытые вопросы

1. Требуется ли полная совместимость с внешними Cesium 3D Tiles или только собственный
   контролируемый поднабор?
2. Какие реальные типы GLB важнее: фотограмметрия, CAD/BIM, отдельные музейные объекты?
3. Нужно ли сохранять объектную семантику и ID между LOD?
4. Допустимы ли внешние общие текстуры или каждый тайл должен быть автономным GLB?
5. Где будет выполняться тайлизация: локальный CLI, серверная задача или CI?
6. Какой минимальный набор браузеров и мобильных устройств обязателен?
7. Нужен ли режим офлайн-кэша?
8. Какой размер исходных моделей и целевое время до первого кадра считать основным
   сценарием?

## Предварительное решение

Для первого прототипа:

- PlayCanvas runtime внутри текущего viewer;
