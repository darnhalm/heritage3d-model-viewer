# Тайлизация GLB в PlayCanvas Model Viewer

Статус: **прототип работает** — тайловый слой в `src/tiles/`, включая implicit tiling; на
реальном тайлсете из Cesium ion проверен. Ниже сначала исходная концепция (она не
переписывалась), затем раздел «Состояние работы» с фактами по итогам реализации.

## Задача

Добавить в текущий PlayCanvas Model Viewer потоковый показ больших glTF/GLB-сцен:
вместо загрузки одного монолитного GLB вьюер получает небольшое дерево GLB-тайлов,
показывает подходящий уровень детализации и выгружает невидимые данные.

Цель — ограничить:

- время до первого содержательного кадра;
- объём одновременно занятой CPU/GPU-памяти;
- число видимых треугольников и draw calls;
- сетевой трафик при перемещении камеры.

Общий размер набора данных при этом может быть намного больше доступной памяти браузера.

## Текущий контекст

Этот репозиторий уже построен на PlayCanvas. Текущая загрузка glTF находится в
`src/viewer.ts`: модель создаётся как `container` asset, а сцена — через
`instantiateRenderEntity()`. Там же рассчитываются `sceneBounds` и
`dynamicSceneBounds`.

Переданный отдельно минифицированный `app.js` использует Three.js, `GLTFLoader` и
`TilesRenderer`. Его полезно рассматривать как референс поведения:

- иерархический выбор тайлов;
- frustum culling;
- оценка экранной ошибки;
- загрузка и выгрузка контента;
- обновление набора тайлов при движении камеры.

Код Three.js переносить напрямую не нужно. Менеджер тайлов должен использовать нативные
Asset, Entity, Render Component, BoundingBox и Frustum API PlayCanvas.

## Главный принцип

Тайлизация выполняется **до открытия модели во вьюере**:

```text
исходный GLB
    ↓
офлайн-конвертер
    ↓
tileset.json + GLB-тайлы нескольких LOD
    ↓
Object Storage / CDN
    ↓
PlayCanvas TileManager
```

Делить большой GLB в браузере не планируется. Это потребовало бы сначала скачать и
распаковать всю модель, то есть не решило бы основную проблему.

## Предлагаемый формат

На первом этапе стоит поддержать небольшой практический поднабор формата 3D Tiles:

- `asset.version`;
- `root`;
- `boundingVolume.box` и затем `boundingVolume.sphere`;
- `geometricError`;
- `refine: "REPLACE"`; позже — `"ADD"`;
- `content.uri`;
- `children`;
- `transform`.

Контентом тайла будет обычный `.glb`, без обязательного контейнера `.b3dm`.

Пример:

```json
{
  "asset": {
    "version": "1.1",
    "generator": "heritage3d-glb-tiler"
  },
  "geometricError": 24,
  "root": {
    "boundingVolume": {
      "box": [0, 4, 0, 20, 0, 0, 0, 8, 0, 0, 0, 20]
    },
    "geometricError": 12,
    "refine": "REPLACE",
    "content": {
      "uri": "tiles/root.glb"
    },
    "children": []
  }
}
```

Совместимость с базовой структурой 3D Tiles позволит:

- проверять наборы сторонними инструментами;
- использовать уже существующие тайлсеты, если их расширения укладываются в выбранный
  поднабор;
- не изобретать собственную схему для bounds, transforms, LOD и refinement.

Полную поддержку спецификации 3D Tiles в MVP закладывать не нужно. В частности, можно
отложить implicit tiling, multiple contents, metadata, внешние tileset JSON и специальные
контейнеры контента.

> По факту реализации: implicit tiling, несколько контентов на тайл, внешние тайлсеты и
> `.b3dm` **сделаны** — без них не открывался ни один реальный набор. Не сделаны `region` и
> `.pnts` / `.i3dm` / `.cmpt`. См. «Состояние работы».

## Стратегия: один стандарт на меши и сплаты

Выбор в пользу подмножества 3D Tiles (раздел выше) в 2026 стал ещё выгоднее, чем выглядел:
стандарт теперь покрывает не только меши, но и гауссовы сплаты.

- Khronos выпустил [`KHR_gaussian_splatting`](https://www.khronos.org/news/press/gltf-gaussian-splatting-press-release) —
  расширение glTF 2.0 для хранения сплатов (участники: Cesium/Bentley, Autodesk, Esri,
  Huawei, Niantic Spatial, NVIDIA, XGRIDS). Компрессия вынесена в отдельное
  `KHR_gaussian_splatting_compression_spz_2`, то есть **SPZ стал штатным компрессором glTF**.
- Cesium в апреле 2026 добавил [иерархический LOD для сплатов через 3D Tiles](https://cesium.com/blog/2026/04/27/3d-gaussian-splats-lod/)
  в CesiumJS, Cesium for Unreal и ion.

Практический вывод: **та же иерархия tileset'а может нести и меши, и сплаты**, и второй
пайплайн строить не надо. Наш `Streamed SOG` при этом остаётся вендорной ветвью, которая
работает сегодня, а 3D Tiles — стратегической, к которой идёт отрасль.

### Как это ложится на PlayCanvas

Полезная деталь: unified gsplat сортирует **несколько компонентов вместе** одним проходом —
в этом его смысл. Значит tile manager может монтировать сплат-тайл отдельным
gsplat-компонентом и всё равно получать глобальную сортировку и общий `splatBudget`, не
изобретая своей сортировки.

Это гипотеза, а не проверенный факт: частое монтирование и снятие компонентов может
колотить work buffer движка. Проверяется замером до того, как на этом строить архитектуру.

### Пробелы в движке (проверено на playcanvas 2.20.6)

| Что нужно | Состояние |
|---|---|
| `tileset.json`, `geometricError`, иерархия тайлов | **нет** в движке — реализовано у нас, `src/tiles/` |
| `KHR_gaussian_splatting` | **нет** (в glb-парсере: draco, basisu, materials_*, lights_punctual, variants) |
| `KHR_gaussian_splatting_compression_spz_2` | **нет** (наш вьюер декодирует SPZ сам, отдельным путём) |
| Приоритет загрузки тайлов | **нет** — `GSplatAssetLoader` это FIFO с `maxConcurrentLoads = 2` |

Первые три пункта означают, что «перейти на стандарт» — это работа, а не настройка: тайловый
слой пишем мы (это и есть предмет этого документа), а сплаты в glTF придётся ждать от
движка либо декодировать самим, как мы уже делаем с SPZ.

### Что просить в апстриме

1. **`KHR_gaussian_splatting` в glTF-парсере.** Расширение ратифицировано Khronos, движку
   его так или иначе делать; для нас это удваивает ценность тайлового слоя.
2. **Приоритет и параллелизм в загрузчике тайлов сплатов.** Данные уже есть:
   `evaluateNodeLods` считает `worldDistance` для каждого узла и умеет штрафовать «за
   спиной» через `lodBehindPenalty`, но до `GSplatAssetLoader` это не доходит, и очередь
   остаётся FIFO. Нужна сортировка перед выдачей задач (как в разделе про
   3DTilesRendererJS) и настраиваемый `maxConcurrentLoads`.

## Офлайн-тайлизатор

Раз формат стандартный, конвертер не обязательно писать с нуля. До того как браться за свой,
стоит проверить готовые: официальный `3d-tiles-tools` от CesiumGS, `py3dtiles`, тайлизацию в
Cesium ion.

> По факту проверки: `3d-tiles-tools` и `py3dtiles` нашу задачу не решают, зато решают
> **Cesium ion** и **Obj2Tiles**. Своего конвертера писать не нужно. Подробности с цифрами —
> в разделах «Шаг 2» и «Шаг 3».

Ниже — требования к тайлизации независимо от того, чей код её выполняет.

### 1. Нормализация исходной модели

Перед разбиением нужно:

- применить или корректно сохранить transform узлов;
- привести геометрию к одной согласованной системе координат;
- вычислить world-space bounds;
- сохранить материалы, UV, normals, tangents и vertex colors;
- определить единицы модели, не меняя их без явной настройки;
- проверить анимации, skinning и morph targets.

Первая версия может официально поддерживать только статическую геометрию. Разбиение
анимированных и skinned-моделей по пространству существенно сложнее.

### 2. Пространственное дерево

Базовый вариант — octree:

- корень содержит bounds всей сцены;
- узел делится на восемь дочерних областей;
- деление продолжается, пока не выполнены бюджеты тайла;
- слишком пустые или мелкие ветви не создаются.

Для преимущественно плоских объектов можно позднее добавить quadtree или адаптивное BVH.
Для MVP octree проще и достаточно универсален.

Предварительные целевые бюджеты одного листового тайла:

| Параметр | Стартовое значение |
|---|---:|
| Треугольники | 50–200 тыс. |
| Несжатый GPU-объём | 10–40 МБ |
| Размер GLB по сети | 1–10 МБ |
| Материалы / draw calls | желательно до 10–30 |

Это настройки конвертера, а не жёсткие ограничения формата.

### 3. Геометрия на границах

Меши, пересекающие несколько областей, — ключевой вопрос тайлизатора.

Возможные стратегии:

1. Назначать целый mesh по центру bounds. Просто, но крупный mesh может разрушить
   пространственное разбиение.
2. Дублировать mesh в пересекающихся тайлах. Просто в runtime, но увеличивает размер и
   может давать наложение геометрии.
3. Разрезать геометрию по треугольникам и пересобрать vertex/index buffers. Это основной
   кандидат для статических heritage/scan-моделей.
4. Сначала разделять по существующим объектам, а слишком крупные объекты дополнительно
   резать по треугольникам. Это наиболее практичный гибрид.

Для MVP предлагается гибридный вариант №4. Треугольник не нужно физически обрезать
плоскостью тайла: достаточно целиком назначить его области по центроиду. Это может немного
расширить фактические bounds тайла, поэтому bounds следует вычислять после разбиения по
реальной геометрии, а не брать геометрическую ячейку octree.

### 4. Уровни детализации

При `REPLACE` родитель содержит упрощённое представление всего поддерева, а дети —
более детальную геометрию.

Возможная цепочка:

```text
LOD 0: очень грубая модель всей сцены
LOD 1: крупные регионы
LOD 2: средние регионы
LOD 3: детальные листовые тайлы
```

Для каждого узла сохраняются:

- GLB его текущего представления;
- точный bounding volume;
- `geometricError`;
- ссылки на дочерние узлы.

Первый полезный кадр должен требовать скачивания только корневого или нескольких
верхнеуровневых GLB.

Упрощение геометрии должно по возможности:

- сохранять границы и UV-швы;
- не разрушать normals;
- учитывать материал;
- не создавать щели между соседними областями;
- иметь измеряемую ошибку, из которой можно получить `geometricError`.

### 5. Материалы и текстуры

Встраивание одинаковых текстур в каждый GLB проще, но быстро создаёт дубликаты. Возможные
этапы оптимизации:

1. MVP: самодостаточные GLB с embedded-текстурами.
2. KTX2/Basis для уменьшения сети и GPU-памяти.
3. Общие внешние текстуры, кэшируемые браузером.
4. Атласы по материалу или региону.

При сборке желательно объединять совместимые primitives с одинаковым материалом.
Для реального FPS это часто важнее дополнительного уменьшения числа треугольников.

### 6. Сжатие

Следует отдельно измерить:

- Meshopt: обычно удобен для потоковой доставки и быстрого декодирования;
- Draco: может дать меньший файл, но требует CPU-времени на декодирование;
- KTX2/Basis: основной кандидат для текстур.

Сжатый размер файла нельзя использовать как оценку памяти. Кэш должен учитывать хотя бы
приблизительный декодированный объём vertex/index buffers и текстур.

## Runtime в PlayCanvas

### Предлагаемые модули

```text
src/tiles/
├── tile-types.ts          типы tileset.json и runtime-состояния
├── tileset-loader.ts      загрузка и проверка JSON
├── tile-manager.ts        обход дерева и общий жизненный цикл
├── tile-selector.ts       frustum + SSE + refinement
├── tile-content.ts        PlayCanvas Asset/Entity для одного GLB
├── tile-request-queue.ts  приоритеты, лимиты, отмена
├── tile-cache.ts          LRU и бюджеты памяти
└── tile-debug.ts          bounds, LOD-цвета и статистика
```

На первом этапе модули можно интегрировать через `Viewer`, но не следует добавлять всю
логику прямо в уже крупный `src/viewer.ts`.

### Жизненный цикл тайла

```text
UNLOADED
    ↓ запрос
QUEUED
    ↓ началась загрузка
LOADING
    ↓ GLB создан
READY
    ↓ выбран для кадра
VISIBLE
    ↓ больше не нужен
READY
    ↓ вытеснен из кэша
UNLOADED
```

Дополнительно нужны состояния `FAILED` и, возможно, `ABORTED`.

`TileContent` должен владеть:

- PlayCanvas `Asset`;
- созданной `Entity`;
- оценкой CPU/GPU-памяти;
- временем последнего использования;
- безопасным `destroy/unload`, не затрагивающим ресурсы других тайлов.

Нужно отдельно проверить совместно используемые текстуры: нельзя уничтожить общий asset,
пока на него ссылается другой видимый тайл.

### Выбор LOD

Основная метрика — screen-space error:

```text
SSE = geometricError * viewportHeight
      / (distance * 2 * tan(verticalFov / 2))
```

Если SSE выше порога, узел нужно уточнять дочерними тайлами. Начальное значение порога
можно взять в диапазоне 8–24 пикселей и затем подобрать на реальных моделях.

При выборе учитываются:

- пересечение bounding volume с frustum камеры;
- расстояние до bounding volume, а не только до его центра;
- SSE;
- доступность дочернего контента;
- сетевой и memory budget;
- направление и скорость движения камеры.

Тайлы в центре экрана и ближайшие к камере получают больший приоритет загрузки.

### Переключение без дыр

Для `REPLACE` нельзя скрывать родителя, пока все необходимые дети не готовы. Безопасная
последовательность:

1. Родитель остаётся видимым.
2. Дети загружаются.
3. Когда нужный набор детей готов, дети показываются.
4. Родитель скрывается.

При обратном переходе сначала показывается готовый родитель, затем скрываются дети.

Небольшой hysteresis для порога SSE предотвратит постоянное переключение LOD на границе.
Короткий cross-fade можно добавить позже, если он не создаёт прозрачностных артефактов и
лишних draw calls.

### Очередь запросов

Начальные параметры:

| Параметр | Desktop | Mobile |
|---|---:|---:|
| Одновременные загрузки GLB | 6–8 | 3–4 |
| Одновременное декодирование | 2–4 | 1–2 |
| Предзагрузка соседних тайлов | ограниченная | выключена или минимальная |

загрузки. Возможность настоящей отмены зависит от используемого пути PlayCanvas Asset API;
как минимум результат устаревшего запроса не должен автоматически становиться видимым.

### Референс: приоритеты в 3DTilesRendererJS

Ниже — как порядок загрузки и выгрузки устроен в [3DTilesRendererJS](https://github.com/NASA-AMMOS/3DTilesRendererJS)
(тот самый `TilesRenderer` из переданного примера на Three.js). Описано поведение по
исходникам, код не переносится: библиотека под Apache-2.0, а нам нужны сами правила.

**Что считается на каждый тайл каждый кадр** (`TilesRenderer.calculateTileViewError`):

- `distanceFromCamera` — расстояние до **ближайшей точки** bounding volume
  (`boundingVolume.distanceToPoint`), минимум по всем активным камерам;
- `error` — screen-space error: `geometricError / (distance * sseDenominator)`, при
  `distance === 0` берётся `Infinity`;
- `inFrustum` / `inView` — пересекает ли объём фрустум камеры.

Важная деталь: если тайл не видит ни одна камера, метрики всё равно записываются — берутся
худшие (максимальная ошибка, минимальное расстояние) именно «для приоритета загрузки».
Невидимые тайлы не исключаются из очереди, они просто проигрывают видимым. Раскрытие детей
идёт, пока `error > errorTarget` (в библиотеке дефолт — 16 пикселей).

**Очередь загрузки — приоритетная, а не FIFO.** `PriorityQueue` с `maxJobs = 25`, и
сортировка вызывается **перед каждой выдачей задач**, а не один раз при постановке: порядок
пересчитывается по свежим данным камеры, поэтому уход камеры автоматически «топит» уже
стоящие в очереди далёкие тайлы.

Компаратор по умолчанию (`errorPriorityCallback`), ступени сверху вниз:

1. явный `tile.priority`, если задан;
2. `used` — тайл, попавший в обход этого кадра, раньше не попавшего;
3. `error` — **больше экранная ошибка, раньше грузим** (сильнее портит картинку);
4. `distanceFromCamera` — ближе, раньше;
5. `depthFromRenderedParent` — мельче глубина, раньше (родитель до детей).

Второй режим (`distancePriorityCallback`, когда предки не подгружаются): `used` →
**`inFrustum`** → внешние tileset'ы → расстояние → глубина. Здесь «в кадре» — отдельная
ступень сортировки, что ближе к тому, что нужно нам.

**Выгрузка — тоже по лестнице** (`LRUCache.unloadPriorityCallback`), см. «Кэш и память» ниже:

1. давно не посещавшиеся (`lastFrameVisited`) — первыми;
2. более глубокие — раньше, чтобы родитель не исчез до детей;
3. те, что раньше по стадии загрузки;
4. внешние tileset'ы — последними;
5. при прочих равных — с меньшей ошибкой.

**Что из этого берём.** Наши разделы «Выбор LOD», «Очередь запросов» и «Кэш и память» выше
описывают те же величины словами; лестницы выше дают им однозначный порядок, который можно
реализовать без домыслов. Два вывода, которые стоит держать в голове при реализации:

- приоритет должен пересчитываться, а не фиксироваться при постановке в очередь —
  иначе камера уехала, а очередь ещё десять секунд грузит то, что было актуально раньше;
- «в кадре» и «за спиной» полезнее как **ступень сортировки**, чем как жёсткий фильтр:
  фильтр даёт пустые области при резком повороте, сортировка — лишь отложенную загрузку.

**Чего этого нет в gsplat-пайплайне движка** (важно, потому что там та же задача уже
решается): `GSplatAssetLoader` — обычная FIFO (`_loadQueue.push` / `shift`) с
`maxConcurrentLoads = 2` и без приоритета, а порядок постановки задаётся обходом узлов по
индексу в `applyLodChanges`. При этом `evaluateNodeLods` уже вычисляет для каждого узла
`worldDistance` и учитывает направление взгляда через `lodBehindPenalty` — то есть данные
для приоритета в рантайме есть, они просто не доходят до загрузчика. Если делать
GLB-тайлизацию, эту границу стоит с самого начала проектировать иначе: менеджер тайлов
обязан передавать в загрузчик расстояние и признак «в кадре».

### Кэш и память

Нужны два ограничения:

- максимальное число готовых невидимых тайлов;
- приблизительный лимит декодированной памяти.

Кандидаты для вытеснения:

1. невидимые;
2. давно не использованные;
3. далёкие от камеры;
4. имеющие готового родителя, который может их заменить.

Видимый тайл нельзя выгружать до появления допустимой замены.

Начальные ориентиры, которые обязательно уточняются профилированием:

| Платформа | Кэш декодированных тайлов |
|---|---:|
| Desktop | 512–1024 МБ |
| Mobile | 128–256 МБ |

Автоматический выбор профиля можно связать с типом устройства и доступной информацией о
памяти, но пользовательская настройка должна иметь приоритет.

## Бюджеты кадра

Для цели 60 FPS один кадр имеет 16,7 мс. Обход дерева не должен занимать заметную часть
этого бюджета, поэтому:

- обновлять selection каждый кадр только при движении камеры или изменении viewport;
- тяжёлые операции распределять по кадрам;
- не создавать и не уничтожать много Entity в одном кадре;
- заранее хранить bounds и не пересчитывать их по всей геометрии;
- ограничить число одновременно активируемых тайлов.

Предварительные ориентиры видимого набора:

| Платформа | Треугольники | Draw calls |
|---|---:|---:|
| Мощный desktop | 2–5 млн | 300–700 |
| Средний ноутбук | 1–3 млн | 200–500 |
| Современный телефон | 0,3–1 млн | 80–200 |

Это не обещание FPS, а стартовые рамки для тестов. Освещение, тени, overdraw, размер
текстур и количество материалов могут оказаться важнее числа треугольников.

## Интеграция с возможностями viewer

### Scene bounds и камера

Корневой bounding volume должен сразу задавать `sceneBounds`, не дожидаясь загрузки всех
GLB. Это позволит:

- корректно выполнить fit camera;
- настроить near/far;
- вычислить скорость камеры;
- настроить grid, shadow distance и dimension box.

`dynamicSceneBounds` для тайлсета не следует пересчитывать только по текущим видимым
тайлам: иначе bounds и связанные настройки будут прыгать при смене LOD.

### Picking, измерения и hotspots

Raycast должен выполняться только по видимым Render Components.

Нужно определить стабильность идентификаторов объектов между LOD:

- если идентификатор нужен только для визуального попадания, достаточно текущего mesh;
- если к объекту привязаны hotspot, измерение или внешние metadata, нужен стабильный ID,
  одинаковый или сопоставимый между уровнями детализации.

Для измерений предпочтительно попадать в самый детальный уже загруженный тайл. При
недостаточном LOD интерфейс может временно запросить уточнение области.

### Alignment и transform

Transform всего тайлсета должен применяться к одному корневому Entity. Локальные
`transform` узлов tileset применяются ниже него. Это позволит сохранить текущие
инструменты перемещения, вращения и масштаба модели без модификации каждого GLB.

### Загрузка URL

`.json` уже используется в интерфейсе для нескольких видов данных, поэтому tileset нужно
распознавать по структуре (`asset`, `root`, `geometricError`), а не только по расширению.

Относительные `content.uri` разрешаются относительно URL текущего `tileset.json`.
Object Storage/CDN должен возвращать корректный CORS и MIME type.

## Диагностика

Для разработки нужен debug overlay:

- FPS и CPU frame time;
- число выбранных, видимых, загружаемых и закэшированных тайлов;
- видимые треугольники и draw calls, насколько это доступно;
- сетевой объём;
- приблизительная память кэша;
- текущий SSE threshold;
- цветовая раскраска LOD;
- визуализация bounding boxes;
- причины выбора/отбрасывания тайла.

Без этой информации настройка тайлизатора и runtime превратится в угадывание.

## Ошибки и деградация

Runtime должен:

- оставлять родительский LOD при ошибке загрузки ребёнка;
- повторять временные сетевые ошибки с ограниченным backoff;
- не повторять бесконечно 404 и ошибки формата;
- показывать понятную ошибку, если не загрузился корень;
- продолжать работу при повреждении отдельной необязательной ветви;
- очищать частично созданные Assets и Entities после ошибки.

## Этапы реализации

### Этап 0. Набор тестовых данных

## Критерии успешного прототипа

- корневой LOD появляется без загрузки всей сцены;
- при приближении камера получает более детальные тайлы;
- при удалении детали освобождаются из кэша;
- переключение `REPLACE` не создаёт пустых областей;
- возврат камеры использует кэш без повторного скачивания;
- bounds и camera fit не меняются при переключении LOD;
- повреждение дочернего тайла не скрывает доступный родитель;
- на тестовой модели собираются метрики времени первого кадра, FPS, сети и памяти.

# Состояние работы (для продолжения с чистого листа)

Раздел-передача по теме тайлов целиком — и по GLB, и по сплатам. Обновляйте по мере работы.
Парный документ по сплат-конвейеру: [`MAKE-LOD.md`](./MAKE-LOD.md).

## Два независимых трека

| | Сплаты | GLB |
|---|---|---|
| Формат | Streamed SOG (`lod-meta.json` + тайлы), вендорный | 3D Tiles 1.1, подмножество (см. «Предлагаемый формат») |
| Конвертер | **работает**: `scripts/make-lod.sh`, прогнан на 8.24 млн сплатов | **чужой, Obj2Tiles**: 1 млн треугольников за 59 с, своего писать не нужно |
| Рантайм | **работает**: движок умеет сам, включается загрузкой `lod-meta.json` | **свой, прототип** в `src/tiles/` — движок `tileset.json` по-прежнему не знает |
| Что болит | порядок загрузки тайлов (FIFO без приоритета) | нет `region`; не проверено на очень больших наборах |

Главный вывод: **это разные проекты**. Сплаты работают в проде сегодня; GLB-тайлизация —
прототип, который уже показывает реальный heritage-скан тайлами (первая картинка за 5.7 с
вместо 16.6 с), но в прод не выведен.

## Что уже проверено по коду движка (playcanvas 2.20.6)

- `tileset.json`, `geometricError`, иерархия тайлов — **нет** (реализовано у нас, `src/tiles/`);
- `KHR_gaussian_splatting`, `KHR_gaussian_splatting_compression_spz_2` — **нет**
  (в glb-парсере: draco, basisu, materials_*, lights_punctual, texture_transform, variants);
- выбор LOD у сплатов: `GSplatOctreeInstance.evaluateNodeLods` — расстояние до ближайшей
  точки AABB × поправка FOV, плюс штраф «за спиной» при `lodBehindPenalty > 1`;
- загрузчик тайлов сплатов: `GSplatAssetLoader` — FIFO (`_loadQueue.push` / `shift`),
  `maxConcurrentLoads = 2`, без приоритета и без пересортировки;
- порядок постановки в очередь — обход узлов по индексу в `applyLodChanges`, не по камере
  (подтверждено на проде: тайлы приходят `6_0 → 5_0 → 4_0 → 3_0 → 3_1 → 3_2 → 2_4 → 4_1 …`,
  то есть грубые уровни сначала, дальше узлы по индексу);
- frustum culling есть, но живёт в рендерере (`gsplat-hybrid-renderer`, interval compaction)
  и **на загрузку не влияет** — тайлы вне экрана всё равно качаются;
- unified gsplat сортирует **несколько компонентов вместе** одним проходом (заявлено в
  документации движка; на нашей сцене это не проверялось).

Что мы включили во вьюере по итогам: `lodBehindPenalty = 5` и `lodUpdateAngle = 90` в
`Viewer.initGSplat` (коммит `f905b08`, на проде). Замер «до/после» не делался — headless-панель
рендерит ~20 кадров и `stats.frame.gsplats` остаётся нулём; сравнивать нужно интерактивно,
переключая `viewer.app.scene.gsplat.lodBehindPenalty` в консоли (1 — как было, 5 — как сейчас).

## Шаг 1: прототип рантайма (сделано)

Главный вопрос — «реализуем ли тайловый слой на PlayCanvas и какой ценой» — закрыт:
**реализуем**, ценой примерно 900 строк своего кода поверх штатного container-ассета.
Движок не трогали, форк не нужен.

**Что лежит в репозитории**

| Где | Что |
|---|---|
| `src/tiles/tileset-loader.ts` | загрузка `tileset.json`, разворачивание в дерево, накопление трансформаций |
| `src/tiles/tile-math.ts` | OBB, расстояние до ближайшей точки габаритов, экранная ошибка |
| `src/tiles/tile-manager.ts` | обход, выбор LOD, показ/скрытие, вытеснение, системы координат |
| `src/tiles/tile-content.ts` | GLB через container-ассет, распаковка `.b3dm`, `RTC_CENTER` |
| `src/tiles/tile-request-queue.ts` | приоритетная очередь с пересортировкой перед выдачей |
| `src/viewer.ts` | `isTilesetFilename`, `loadTileset`, вызов из `update`, габариты, сброс сцены |
| `tests/tiles.spec.ts` | четыре теста на сэмплах |
| `scripts/fetch-3d-tiles-samples.sh` | кладёт сэмплы в `dist/models/3d-tiles/` (в git не попадают) |

Открывается так же, как модель: `?load=models/3d-tiles/1.1/MetadataGranularities/tileset.json`.
Тайлсет опознаётся **по имени файла** (`tileset.json` или `*-tileset.json`) — расширение
`.json` во вьюере уже занято сплатовым `lod-meta.json`.

**Поправка к оценке сэмплов.** Выше было записано «27 `tileset.json`, есть `1.1/` и
`TilesetWithDiscreteLOD`». Формально верно, но выбирать почти не из чего: в `1.1/` два
набора из четырёх — implicit tiling (`SparseImplicitQuadtree`, `SparseImplicitOctree`), а
единственный сэмпл с настоящей цепочкой уровней — `TilesetWithDiscreteLOD` — это 1.0 с
контентом `.b3dm`. Поэтому в прототипе пришлось написать распаковку `.b3dm` (тридцать строк:
заголовок, две таблицы, дальше обычный GLB), иначе проверять переключение LOD было бы не на
чем.

**Что проверено на сэмплах** (тесты в `tests/tiles.spec.ts`, все зелёные):

- 3D Tiles 1.1, `refine: ADD`, несколько `contents` на тайл, локальные координаты
  (`MetadataGranularities`) — рисуется правильно, ориентация верная;
- 3D Tiles 1.0, `refine: REPLACE`, три уровня, контент `.b3dm`, корневой ECEF-трансформ со
  масштабом 100 (`TilesetWithDiscreteLOD`) — уровни переключаются по расстоянию, на экране
  всегда ровно один;
- клик по тайлу: выделение и измерения работают (см. «Мешы тайлов» ниже);
- `resetScene` уносит корневую entity и ассеты тайлов.

**Что НЕ сделано** (осознанно, за пределами вопроса шага 1):

- bounding volume `region` (географический) — такие тайлы считаются всегда видимыми и
  бесконечно грубыми, то есть грузятся всегда;
- `.pnts` / `.i3dm` / `.cmpt`, метаданные `EXT_structural_metadata`, `viewerRequestVolume`;
- cross-fade между уровнями (сейчас переключение мгновенное), бюджет памяти в мегабайтах
  (сейчас лимит по числу тайлов), мобильный профиль параллелизма;
- проверка на действительно большом тайлсете — самое главное из непроверенного: всё, что
  выше, гонялось на трёх тайлах и на двадцати GLB.

**Грабли, найденные при сборке прототипа** (каждая стоила времени):

- **`app.tick` в headless просто останавливается.** У вьюера `autoRender === false`,
  страница ничего не перерисовывает, а `requestAnimationFrame` в headless-Chromium
  привязан к компоновщику — без изменений на экране он перестаёт срабатывать через
  несколько кадров. Обход дерева при этом не видит, что камера переехала. В тестах кадры
  крутятся вручную (`pumpFrames`). Это же, скорее всего, объясняет и загадку из абзаца про
  сплаты выше: headless-панель «рендерит ~20 кадров», а `stats.frame.gsplats` остаётся нулём.
- **`Mat4.data` — это `Float32Array`.** ECEF-координаты (~6.4e6) в float32 дают шаг около
  0.5 единицы. Поэтому тайлсет **сдвигается к началу координат** на корневой entity, а не
  рисуется «как есть»; рецентровка считается по корневому тайлу до построения дерева.
- **Общий временный `Mat4` через две функции.** Разложение матрицы в TRS читало трансляцию
  из той же матрицы, куда до этого писало базис поворота, — контент вставал в нулевую точку
  и уезжал за 6400 км. Симптом: статистика показывает «загружено и выбрано», экран пуст.
- **Мешы тайлов не попадают в инструменты сами.** Выделение, измерения и точки интереса
  работают по списку `viewer.meshInstances`, который собирается один раз после загрузки
  модели. Для тайлов такого списка не существует: набор видимого меняется каждый кадр.
  Добавлен `Viewer.getPickableMeshInstances()` — статический список плюс мешы видимых
  тайлов; глубинный picker (`src/picker.ts`) при этом работает и так, он рисует сцену.
- **`dynamicSceneBounds` считается только в `onPrerender`.** `frameScene` вызывает
  `fitCameraClipPlanes` раньше, чем габариты обновятся, — при загрузке тайлсета их
  приходится посчитать явно, иначе дальняя плоскость отсечения режет сцену пополам.
- **AppleDouble-файлы на внешнем томе.** macOS кладёт рядом с каждым файлом `._имя`;
  Playwright пытался разобрать `tests/._smoke.spec.ts` как тест и падал на всём прогоне.
  В `playwright.config.ts` добавлен `testIgnore: '**/._*'`. Тот же мусор ломает `npm run
  lint` (шесть «Parsing error» на `src/tiles/._*.ts`) — это не чинилось.

**Как посмотреть самому**

```bash
bash scripts/fetch-3d-tiles-samples.sh && npm run build && npm run serve
```

Дальше `http://localhost:3000/?load=models/3d-tiles/1.0/TilesetWithDiscreteLOD/tileset.json`.
Статистика тайлов — `viewer.getTileStats()` в консоли. Тесты (запускать **в один поток**,
параллельные воркеры не успевают за таймаутом):

```bash
npx playwright test tests/tiles.spec.ts --workers=1
```

Отдельно: тест `metadata and poi tabs` в `tests/smoke.spec.ts` падает по таймауту клика и
**до** этих изменений — проверено на сборке из `c6d9d9d`.

## Шаг 2: чужие тайлизаторы (проверено на реальных сканах)

**Главное про наши данные.** Прогон делался на двух heritage-сканах из `dist/models`:

| | череп | доспех Эрика XIV |
|---|---:|---:|
| Файл | 164 МБ | 125 МБ |
| Треугольники | 166 тыс. | 1 млн |
| Вершины | 91 тыс. | 830 тыс. |
| Текстуры | 4 шт., из них PNG на **122 МБ** | 1 шт., PNG на **86 МБ** |
| Габариты | 17 × 16 × 13 (единицы сцены) | 0.37 × 1.67 × 0.69 м |

Отсюда вывод, который меняет постановку задачи: **вес наших моделей — это текстуры, а не
геометрия**. У доспеха на миллион треугольников приходится 86 МБ одной PNG; у черепа
геометрии вообще на копейки. Пространственная нарезка *геометрии* сама по себе не даст почти
ничего — тайлизатор обязан резать и перепаковывать **текстуры**, иначе каждый тайл потянет за
собой ту же гигантскую картинку. Это же объясняет, почему у большинства инструментов
«тайлизация» означает не то, что нужно нам: они писались под аэрофотограмметрию и городские
модели, где всё наоборот.

**Что проверено фактически**

| Инструмент | Версия | Режет большую GLB? | Что на самом деле |
|---|---|---|---|
| `3d-tiles-tools` (CesiumGS) | 1.x, npm | **нет** | конвертер форматов и упаковщик; пространственной нарезки нет ни в одной команде |
| `py3dtiles` | 12.1.1, pip | **нет** | `convert` — только облака точек (`.las/.laz/.xyz/.ply`); `export` — WKB-мультиполигоны из PostGIS, без текстур |
| `vtkCesium3DTilesWriter` (VTK) | 9.6.2, pip | **не запускается** | SIGSEGV на mesh-пути, в том числе на простой сфере без текстур и при любом CRS. И даже по документации Kitware уровней детализации у него нет — «future work» |
| `Obj2Tiles` (OpenDroneMap) | 1.6.2, сборка из исходников | **да, проверено** | 1 млн треугольников + 86 МБ текстуры → 337 тайлов за 59 с; наш рантайм открывает результат без правок |
| Cesium ion | — | — | **не проверен**: упёрлись в права токена, см. ниже |

Подробности, которые стоит знать:

- **`3d-tiles-tools`** делает `createTilesetJson` — тайлсет из готовых файлов, один файл =
  один тайл, без иерархии и уровней. На доспехе отработал за 0.5 с и дал корректный
  bounding volume (проверено против матрицы корневого узла — у Sketchfab-моделей там масштаб
  0.048, из-за которого «сырые» габариты из аксессоров и габариты сцены различаются в 20 раз).
  Контент рядом с `tileset.json` он **не копирует** — путь в `content.uri` нужно поправлять
  руками. Как тайлизатор непригоден, как посттул (upgrade 1.0→1.1, b3dm↔glb, merge, 3tz) —
  вполне.
- **`py3dtiles`** — инструмент для облаков точек и городских слоёв; текстурированный меш в
  него просто нечем подать.
- **VTK** — падение воспроизводится на `pip install vtk` (macOS arm64) за три строки; можно
  предположить, что в сборке из исходников с их `tiler.py` он работает, но проверять смысла
  мало: без LOD это только разрезание на куски.
### Obj2Tiles: прогон на доспехе

Единственный кандидат, который делает ровно нужное, и он **работает**.

Официального образа в GHCR нет (`ghcr.io/opendronemap/obj2tiles` отдаёт 401), поэтому образ
собирается из репозитория — Dockerfile там свой, нативная сборка под arm64:

```bash
git clone --depth 1 https://github.com/OpenDroneMap/Obj2Tiles.git && cd Obj2Tiles
docker build -t obj2tiles:local .
docker run --rm -v "$PWD":/data obj2tiles:local /data/in/model.obj /data/out \
    --local --octree --lods 3 --divisions 2 --use-system-temp
```

Вход — **только OBJ**. Наш GLB готовится `trimesh` за 7 секунд (96 МБ OBJ + 86 МБ PNG рядом).

**Что получилось на доспехе** (1 млн треугольников, 86 МБ текстуры):

| | значение |
|---|---|
| Время конвертации | **59 с** целиком (decimation + splitting + tiling), 8 ядер |
| Тайлов | **337**: 1 → 16 → 64 → 256 по уровням, `refine: REPLACE`, box-габариты |
| Объём | 122 МБ против 125 МБ исходных — сжатия нет, но теперь это 337 файлов |
| Корень | `root.b3dm` 10.7 МБ: 333 тыс. треугольников с текстурой 256×256 |
| Средний уровень | ~11 тыс. треугольников на тайл, текстура 1024×1024 (JPEG) |
| Лист | ~2.9 тыс. треугольников, свой атлас (PNG), 70–500 КБ на файл |
| `asset.version` | 1.0, контент `b3dm` — **наш рантайм читает как есть** |
| `transform` корня | единичная матрица (режим `--local`) |

**Как это выглядит у нас**: 337 тайлов, **0 ошибок**, ориентация и масштаб верные (доспех
1.67 м), вблизи видны гравировка и золочение, швов на границах тайлов не заметно.

| | один тайл (`3d-tiles-tools`) | 337 тайлов (Obj2Tiles) |
|---|---:|---:|
| До первой геометрии на экране | **16.6 с** | **5.7 с** |
| Скачано к этому моменту | 125 МБ | 2.4–9 МБ |
| При полном приближении | 125 МБ | ~110 МБ, 202 тайла в кадре |

То есть выигрыш ровно там, где ожидался: первая картинка приходит втрое быстрее и на два
порядка меньших данных. На максимальном приближении суммарный объём тот же — тайлы не
сжимают, они распределяют во времени.

**Что стоит покрутить дальше**: `root.b3dm` в 10.7 МБ — сейчас главный тормоз первой
картинки, и это **геометрия** (333 тыс. треугольников), а не текстура (256×256, 16 КБ);
степень упрощения на грубых уровнях явно стоит поднять. Есть `--no-root-content` (проверено:
работает, первые тайлы приходят за 5.7 с при 9 МБ), `--texture-format Webp|Ktx2`
(KHR_texture_basisu — движок его умеет), `--max-texture-size` (по умолчанию 4096, то есть
исходную текстуру он ужимает) и `--texture-quality` (JPEG 75 по умолчанию — потеря качества
против исходного PNG заметна на глаз при сравнении).

Два «но» по самому инструменту: вход **только OBJ** и лицензия **AGPL-3.0** — как отдельная
CLI в конвейере сборки она не затрагивает код вьюера, но решение стоит принимать осознанно.

**Заодно проверили рантайм на реальном скане.** Однотайловый тайлсет из `3d-tiles-tools`,
125 МБ в одном `content` — открывается, ориентация и масштаб верные (габариты 0.59 × 1.78 ×
0.97 м, доспех в натуральную величину), текстура на месте. **16.6 с до первой геометрии** с
локального сервера. Это ровно та боль, ради которой затевались тайлы.

**Найдено по ходу и исправлено в рантайме**: при `REPLACE` тайл без собственного контента
(`--no-root-content` и любые пустые группирующие узлы) закрывал собой недогруженных детей —
на экране было пусто, пока не готовы все. Теперь пустой узел не считается «закрывающим», и
дети проявляются по мере готовности. Тестом это не покрыто: чтобы поймать разницу, нужно
поймать промежуточное состояние загрузки.

### Cesium ion: чего не хватило

Заливка не состоялась по прозаичной причине — у выданного токена оказались только права
`assets:read` и `geocode`. `GET /v1/me` отвечает, а `GET /v1/assets` и `POST /v1/assets`
дают `404 ResourceNotFound` (шлюз ion прячет маршруты, на которые нет прав, а не отвечает
403 — на это легко потратить время, решив, что сменился адрес API).

Чтобы продолжить, нужен токен со скоупами **`assets:read` + `assets:write` + `assets:list`**.
Дальше по документации: `POST /v1/assets` с `type: "3DTILES"` и `options.sourceType:
"3D_CAPTURE"`, загрузка в выданное S3-хранилище, `POST /v1/assets/{id}/uploadComplete`,
опрос статуса через `GET /v1/assets/{id}`.

Отдельный вопрос, который встанет сразу после: тайлсеты ion отдаются **с авторизацией**
(токен на каждый запрос), а наш загрузчик тайлов ходит за контентом обычным `fetch` без
заголовков. Либо выгружать готовый тайлсет из ion целиком и класть рядом со сценой, либо
учить `tile-content.ts` подставлять токен. Для сравнения качества с Obj2Tiles достаточно
первого.

**Вывод по шагу 2.** Из трёх инструментов, названных в плане, ни один не режет
текстурированный скан. Но **шаг 3 (свой конвертер) не нужен**: Obj2Tiles закрывает задачу
целиком, его выход мы показываем без единой правки, и настраивать в нём есть что. Дальше
имеет смысл не писать своё, а подбирать его параметры под наши сцены — и отдельно решить
вопрос с AGPL и с тем, что вход только OBJ.

## Шаг 3: implicit tiling и тайлсеты из Cesium ion (сделано)

Отправной точкой стал реальный архив из ion — храм, 128 МБ: 552 `.glb`, 185 `.subtree`, один
`tileset.json`. Разбор показал, что почти всё в нём мы уже умели: 3D Tiles 1.1 без
обязательных расширений, габариты `box` с ECEF-трансформом корня (это мы обрабатываем с
рецентровкой), контент `.glb`. Не хватало ровно одного — **implicit tiling**.

**Что оказалось про содержимое тайлов ion.** Внутри `.glb`: `KHR_draco_mesh_compression`,
`KHR_texture_basisu` (KTX2) и **`KHR_materials_unlit`**, нормалей нет вовсе. Все три
расширения движок умеет, декодеры Draco и Basis во вьюере уже подключены (`index.tsx`,
`static/lib/`), так что одиночный тайл открылся как обычная модель без единой правки.

И это же — ответ на вопрос «почему у Obj2Tiles картинка мёртвая». Ion **намеренно** делает
unlit: у фотограмметрии свет запечён в текстуру, освещать её второй раз незачем, нормали не
нужны. А через OBJ получилось худшее из двух миров — материал остался освещаемым, но без
нормалей, поэтому движок считал их пофейсово. Проблема была не «потеряли PBR», а «потеряли
нормали, не пометив материал unlit».

**Что добавлено в рантайм**

| Файл | Что делает |
|---|---|
| `src/tiles/subtree.ts` | бинарный формат `.subtree`: заголовок, JSON-чанк, маски доступности (константа или битовый поток), внешние буферы, индексы Мортона |
| `src/tiles/implicit-tiling.ts` | разворачивание масок в обычные `Tile`: деление корневого ящика по координатам узла, `geometricError = корневая / 2^level`, подстановка `{level}/{x}/{y}/{z}` в шаблоны |
| `src/tiles/tile-manager.ts` | ленивая загрузка поддеревьев по мере обхода |
| `src/tiles/tileset-loader.ts` | «плотные» габариты из метаданных (семантика `TILE_BOUNDING_BOX`) |

Дальше по коду разницы нет: узел неявного дерева — такой же `Tile`, и обход, выбор уровня,
очередь и вытеснение о его происхождении не знают.

**Как проверялось.** Прежде чем писать TypeScript, логика масок была собрана прототипом на
Python и сверена с архивом: обход нашёл **552 тайла из 552**, без лишних и пропущенных. Это
сэкономило отладку в браузере — все последующие ошибки оказались не в математике.

**Результат на храме** (порог 16 пикселей, вьюпорт 720 px):

| Расстояние до модели | Выбрано тайлов | Глубина | Скачано |
|---|---:|---:|---:|
| кадрирование целиком | 1 | 0 | 0.27 МБ |
| 60 м | 11 | 2 | 3.8 МБ |
| 25 м | 37 | 4 | 14 МБ |
| 10 м | 70 | 4 | 37 МБ |
| 4 м | 63 | **5** | 36 МБ |

Ошибок загрузки нет ни на одном шаге. Глубина 5 — это уже **вложенное** поддерево: корневой
файл масок описывает уровни 0–4, дальше подгружаются отдельные `.subtree` (в архиве есть
уровни до 8-го). Вблизи видны розетки на барабане, карниз и швы кровли — то есть доходит
именно исходная детализация.

**Три ошибки, которые стоили времени** (все три записаны, чтобы не повторять):

- **`new URL()` кодирует фигурные скобки.** Шаблон `subtrees/{level}/{x}/{y}/{z}.subtree`,
  разрешённый относительно базы заранее, превращается в `%7Blevel%7D`, и подстановка
  координат перестаёт работать. Порядок обязан быть обратным: сначала подстановка, потом
  разрешение относительно базы. Симптом — дерево из одного узла при живом `tileset.json`.
- **Локальные и глобальные координаты узла.** Маски адресуются координатами внутри
  поддерева, а URI и габариты — глобальными. На корневом поддереве они совпадают, поэтому
  ошибка не видна, а на вложенных всё разъезжается.
- **Маски нельзя грузить по экранной ошибке узла.** Сначала было «загрузить, если нужна
  детализация», и уровень 5 не наступал никогда: у заглушки ошибка 9.9 при пороге 16. Но до
  загрузки масок про узел не известно ни есть ли у него контент, ни есть ли дети —
  единственно верное условие «обход до него дошёл». Заодно такой узел не должен считаться
  «закрывающим» при `REPLACE`, иначе родитель снимет свой контент и оставит дыру.

**Отдельно про кадрирование.** У неявного дерева `boundingVolume` корня всегда кубический и
заметно больше модели: у храма это 115 × 95 × 119 м на постройку вдвое меньше. Камера,
кадрированная по нему, отъезжает так далеко, что детализация не запрашивается вообще. Ion
кладёт рядом «плотные» габариты в метаданных с семантикой `TILE_BOUNDING_BOX` — теперь они
используются для кадрирования, а кубический объём остаётся для отсечения и выбора уровня,
где он и нужен.

### Две правки после первого показа

Первое же кручение камеры в настоящем браузере вскрыло то, чего не видно в headless.

**Чернота при повороте.** При взгляде сверху половина сцены закрывалась чёрным. Виноват
оказался не рантайм тайлов, а **ловитель теней**: он ставит горизонтальную плоскость по низу
габаритов сцены. Под одиночной моделью это ровно то, что нужно, а тайлсет приносит
собственный рельеф — плоскость режет его и закрывает всё, что оказалось ниже. Теперь при
загрузке тайлсета `shadowCatcher.enabled` выключается (настройка остаётся, включить обратно
можно).

**Сцена была завалена на 28°.** Причина тоньше и важнее: мы поворачивали ECEF на `Rx(-90)`,
считая, что это «Z-вверх → Y-вверх». Но Z в ECEF — **земная ось**, а не местная вертикаль,
поэтому «верхом» сцены становилась она, и модель наклонялась на угол, равный дополнению
широты. Теперь перед этим поворотом применяется переход ECEF → ENU (восток-север-верх) в
точке привязки тайлсета: местная вертикаль встаёт вверх. У негеографических наборов (координаты
меньше 1e6) шаг пропускается, и поведение прежнее.

Побочный выигрыш: габариты перестали быть раздутыми. Осеориентированная оболочка повёрнутого
ящика у храма давала 104 × 62 × 106 м вместо реальных 71 × 37 × 73 — камера кадрировалась
заметно дальше, чем нужно.

Обе находки — прямое следствие того, что WebGPU и настоящий браузер в этой работе до сих пор
оставались непроверенными. В headless-Chromium с WebGL2 ни то, ни другое не проявлялось:
чернота требует ловителя теней с тенями, а наклон без интерактивной камеры просто не
бросается в глаза.

**Что это значит для планов.** Своя нарезка не нужна: ion выдаёт именно то, что надо, и мы
это показываем. Obj2Tiles остаётся запасным вариантом для случаев, когда модель нельзя
отдавать наружу, — но тогда придётся либо тащить через него нормали, либо помечать материалы
unlit.

## Пропавшие экранные кнопки на тайлсете (исправлено)

На тайлсете не показывался нижний ряд экранных кнопок — «Инфо», **«Кадрировать сцену»
(центрирование камеры)**, HD, измерения, режим камеры, полный экран. Причина: контейнер
`#popup` получает класс `empty` (и `display:none` из `style.scss`), когда
`scene.nodes === '[]'` (см. `src/ui/popup-panel`). Обычную иерархию заполняет
`postSceneLoad`, а отдельный путь `loadTileset` её не трогал, поэтому `scene.nodes` оставался
пустым и панель пряталась.

Иерархию из 500+ потоковых тайлов показывать бессмысленно (набор меняется каждый кадр),
поэтому `loadTileset` кладёт в `scene.nodes` **один** корневой узел с именем тайлсета —
этого достаточно, чтобы панель появилась и работали кадрирование камеры, инфо и полный
экран. `resetScene` возвращает `scene.nodes` в `[]`, чтобы при удалении тайлсета панель
снова пряталась.

Проверка визуально: в Playwright (там `requestAnimationFrame` идёт по-настоящему) `#popup`
теряет класс `empty` и кнопки появляются. В in-app-браузере подтвердить не удалось —
мост observer→React обновляется по rAF (`src/ui/index.tsx`), а он в headless подвисает
(та же причина, что у рендер-цикла); в обычном браузере всё работает.

## Чёрные тайлы на WebGPU при движении камеры (найдено и исправлено)

Симптом: на тайлсете из ion при вращении/зуме/панорамировании модель заливается чёрным
«сверху текстур», а стоит остановить камеру — картинка возвращается. Только на WebGPU;
на WebGL2 (`?webgl`) дефекта нет.

**Диагностика заняла долго, потому что почти каждая гипотеза оказывалась ложной.** По
порядку отсекались: ловитель теней (его плоскость гасится, чернота осталась); наклон сцены
(отдельный баг, к черноте отношения не имеет); multiframe (при выключенном — тоже чёрное).
Решающими были три наблюдения:

- плоский цвет вместо текстуры — вся модель заливается цветом ⇒ геометрия и глубина целы,
  чернит **сэмплинг emissive-текстуры**;
- при поднятой `emissiveIntensity` дальняя от камеры часть остаётся **ровно** чёрной
  (текстура возвращает ноль), а ближняя — яркой ⇒ дефект **зависит от расстояния**, то есть
  это выбор мип-уровня;
- на неподвижной камере multiframe маскирует дефект своим отрицательным LOD-биасом
  (`textureBias ≈ -2.32`), поэтому баг виден именно в движении.

**Первопричина — баг движка (playcanvas 2.20.6) на WebGPU.** Текстуры KTX2 (Basis) из ion
приходят **без мип-цепочки** — один уровень. Движок всё равно создаёт GPU-текстуру с полной
цепочкой (`calcMipLevelsCount`), заливает только уровень 0, а верхние остаются чёрными. На
скользящем угле сэмплер выбирает эти пустые уровни. Починить «в лоб» мешают две вещи:
публичный сеттер `texture.mipmaps = false` на WebGPU — **пустая ветка** (`if (isWebGPU) {}`),
а к моменту, когда до текстуры доходят руки, GPU-объект уже создан (Basis-транскод идёт во
время загрузки контейнера).

**Фикс** (`src/tiles/tile-content.ts`, `fixCompressedTexture`): у каждой одноуровневой
сжатой текстуры контента (1) правим `_mipmaps` / `_numLevels` напрямую в обход
сеттера-заглушки, ставим `minFilter`/`magFilter` в `FILTER_LINEAR`; (2) **на WebGPU
пересоздаём GPU-объект** (`recreateImpl()`), чтобы он выделил ровно один уровень. Без
пункта (2) правка полей не влияет на уже созданную GPU-текстуру, и чернота остаётся —
это и была главная ловушка. На WebGL2 пересоздание не делается: там дефекта нет.

Проверено вживую на WebGPU: вращение, зум и косые ракурсы храма — черноты нет ни в
движении, ни на статике. WebGL2 по-прежнему чист. Тестом не покрыто: автотесты идут на
WebGL2 (swiftshader), где баг не воспроизводится в принципе, — а разница между WebGPU и
WebGL2 в headless недоступна.

## С чем тайловый рантайм обязан ужиться в этом вьюере

Список составлялся до прототипа; ниже отмечено, что из этого уже сделано, а что осталось
открытым.

- **сделано** — `app.autoRender === false`: менеджер зовёт `renderNextFrame()` сам, но
  только когда изменился набор видимых тайлов. Обход дерева при этом идёт каждый кадр —
  он дешёвый, а лишний `renderNextFrame` на неподвижной сцене стоит кадра каждые 16 мс;
- **сделано** — **bounds**: габариты берутся из корневого bounding volume и не зависят от
  того, какие тайлы сейчас загружены, поэтому `frameScene` и камера не прыгают при смене
  уровня. Добавлено в `calcSceneBounds` отдельной веткой;
- **сделано** — **picking**: глубинный `src/picker.ts` работает с тайлами без изменений (он
  рисует сцену), а вот списочные инструменты — нет, им добавлен
  `Viewer.getPickableMeshInstances()`;
- **не проверено** — **multiframe**: `Viewer.syncMultiframeCamera()`. На сэмплах ничего не
  ломалось, но специально не смотрели, как накопление кадров ведёт себя в момент
  переключения уровня;
- **проверено** — **бэкенд**: тайлсет из ion открыт в настоящем браузере на **WebGPU**;
  автотесты идут на WebGL2 (swiftshader в headless). Именно WebGPU-прогон вскрыл черноту от
  ловителя теней и заваленный горизонт, см. «Две правки после первого показа»;
- **сделано** — модули лежат в `src/tiles/`.

## Пожелания на будущее: отладка 3D Tiles со сплатами

После появления в PlayCanvas поддержки `KHR_gaussian_splatting` подключить сплат-контент к
тому же `TileManager`, не создавая второй независимый набор инструментов. В этом случае
визуализации, основанные на метаданных тайла, должны работать одинаково для мешей и сплатов:

- OBB-контуры, раскраска по состоянию/LOD и HUD статистики;
- изоляция уровня LOD, заморозка отбора и пауза загрузки;
- inspector замороженной камеры с осями и объёмом FOV.

Отдельно потребуется splat-aware picking: существующий `Picker` возвращает `MeshInstance`,
поэтому клик по конкретному сплату/тайлу и измерения по поверхности автоматически не
заработают. Для клика по тайлу допустим первый этап через bounding volume или отдельный
ID-pass, а точные измерения потребуют результата пересечения с отрисованными сплатами.
Обычные standalone `.ply`/`.sog`/`.spz` сейчас идут через отдельный GSplat-пайплайн и не
получают Tiles Debug; объединять их с тайловой отладкой имеет смысл только при появлении у
них тайловой иерархии.

## Отладочная визуализация тайлов

Вешается в слот «слоёв», где для тайлсетов скрыты UV/Geometry. У менеджера на каждый тайл:
мировой OBB, расстояние, экранная ошибка, `inFrustum`, состояние, глубина, порядок в очереди
(`tile-request-queue.ts`). Движок умеет immediate-mode линии/боксы (`DebugLines`). Фазами:

- **Фаза 1 — СДЕЛАНО.** OBB-боксы **активных** тайлов (`state !== unloaded`
  либо выбран обходом; полностью выгруженные не рисуем, иначе на 508 тайлах каша), раскраска
  двумя режимами + живой HUD со `getStats()`. Детали:
  - `DebugLines.obb(center, ax, ay, az, clr)` — рисует 12 рёбер OBB из центра и трёх полуосей
    (`box()` умел только AABB).
  - **Только выбранные тайлы и толстые контуры.** Рисуются **только `tile.selected`**
    (текущий срез LOD, который выдаёт сам механизм по мере приближения) — родительские/грузящиеся
    боксы не показываем, иначе в ближнем приближении оверлей превращался в нечитаемую кашу линий.
    Контуры — **толстые ленты** (`DebugSolid.obbEdgesThick`): каждое ребро OBB рисуется quad-лентой,
    повёрнутой к камере, ширина `~tileLineThickness·0.001·dist` (≈постоянная в пикселях).
    Ползунок «Толщина линий» (`0.5..8`, по умолчанию `2`) меняет её вживую. Режим каркаса:
    ровный цвет текущего State/LOD или шахматная схема с той же палитрой;
    соседние блоки чередуют **яркость** (`dimColor` для чётных по `gridIndex`). В шахматном
    режиме отдельно включается заливка OBB: только затемнённые клетки получают чёрный слой
    с opacity 20%, светлые остаются без заливки; по умолчанию режим выключен.
    Материал контуров `DebugSolid`:
    `BLEND_NORMAL`, `CULLFACE_NONE`, `depthState.write = false`. Заливку **убрали**: объёмная
    заливка bounding-боксов не читалась, а экспериментальная заливка реальной геометрии
    полупрозрачным tint визуально не сработала. Оставлены только контуры.
    Слои/шейдер общие с `DebugLines` (`ensureDebugLayers`/`debugShaderArgs`).
  - **Поверхностная раскраска отключена:** подход CesiumJS `debugColorizeTiles` проверен через
    отдельный overlay по геометрии, но ожидаемого результата в этом рендерере не дал и удалён.
    Вместо неё сделан точный клик по поверхности → усиленный белый OBB соответствующего тайла
    и карточка параметров в HUD. Bounding-боксы крупнее геометрии и «висят» в воздухе — для
    близкого инспекта поверхностная раскраска всё ещё была бы пригоднее.
  - `TileManager.debugDraw(lines, solid, mode)` — обход дерева (следует за `externalRoot`, как
    `visit`), рисует толстые OBB-контуры выбранного среза. Режимы: `state` (выбранный — голубой)
    и `lod` (палитра по `depth`). Цвета — формат `0xAABBGGRR`.
  - Вьюер: `debugTiles: DebugLines` (сейчас пуст) + `debugTilesSolid: DebugSolid` (контуры).
    OBB-контуры обновляются каждый `onPrerender`. HUD — DOM-оверлей `#tile-debug-hud` (левый низ
    канваса), обновляется императивно в `updateTileHud()`, а не через observer.
  - Флаги observer: `debug.tileDebug` (bool), `debug.tileDebugMode` ('state'|'lod'),
    `debug.tileLineThickness` (number, `0.5..8`), `debug.tileLineStyle`
    (`solid`|`checker`), `debug.tileCheckerFill`, `debug.tilePick`,
    `debug.tileIsolatePick` (bool).
    Обработчики просто просят кадр (`renderNextFrame`). UI — категория «Tiles Debug» в
    левой панели (только для тайлсетов), кнопка + переключатель state/LOD; переводы en/ru/zh.
  - Тест: `tests/tiles.spec.ts` → «отладочный оверлей тайлов…» (DISCRETE_LOD): линии
    рисуются, HUD виден с текстом из `getStats()`, регулируется толщина, LOD-режим
    переключается, клик выбирает тайл и выводит его карточку; выключение прячет overlay,
    ViewCube и HUD. Прогонять `--workers=1`.
- **Фаза 2 — СДЕЛАНО.** Заморозка отбора + пауза загрузки. Детали:
  - Заморозка (`TileManager.setFrozen`, флаг `frozen`): при включении атомарно снимаются
    `frustum`/позиция/SSE первой камеры, затем в `update` их пересчёт пропускается — все тайлы
    продолжают отбираться относительно первой камеры. `Viewer` отдельно сохраняет её world-
    матрицу, focus, FOV/aspect/near/far и проекцию в `frozenTileCamera`, после чего автоматически
    переводит живую камеру в боковой inspector-ракурс. При разморозке первая камера возвращается
    в сохранённую позу.
  - **Визуализация камеры СДЕЛАНА:** `debugTileCamera` рисует RGB-оси, направление, ближнее и
    дальнее сечения, рёбра и сетку FOV; `debugTileCameraSolid` — лёгкую полупрозрачную заливку
    объёма через `DebugSolid.frustumFaces`. Перспективная камера показывается усечённой пирамидой,
    ортографическая — параллельным объёмом. Геометрия остаётся на месте, пока inspector-камеру
    свободно двигают.
  - Пауза на уровне очереди (`TileRequestQueue`): флаг `paused` — `dispatch` не стартует
    новые задачи (идущие доигрывают), `setPaused(false)` догоняет очередь. Неработавший
    пользовательский `Step` удалён вместе с `stepLoad`/`stepTileLoading`.
  - **Изоляция уровня LOD** (`TileManager.setLodIsolate`, поле `lodIsolate`): в `visit`
    уточнение идёт **по экранной ошибке, но не глубже `lodIsolate`** (`needsDetail &&
    tile.depth < lodIsolate`), а `selectSelf` выбирает только тайлы глубины `lodIsolate` —
    на экране остаётся **только выбранный уровень**. Ключевое: не форсируем углубление —
    поэтому на больших сценах далёкие фрагменты, до которых SSE не дотягивает, **не грузятся**,
    показываются только видимые вблизи фрагменты уровня (на храме: изоляция 4 издалека — 5 МБ
    вместо 91 МБ). В `debugDraw` при изоляции в оверлей попадают **только выбранные** тайлы. Флаги observer `debug.tileLodLock` (bool) +
    `debug.tileLodLevel` (number), применяются `applyTileLodIsolate`. Верх ползунка —
    `scene.tilesetMaxDepth` = `getTreeDepth()`, обновляется на загрузке и по мере
    разворачивания неявного дерева (в `handleTileChange`). UI — тумблер «Isolate LOD Level»
    + `Slider` в начале категории «Tiles Debug» (независимо от оверлея).
  - Флаги observer `debug.tileFreeze` / `debug.tilePaused` / `debug.tileLodLock` (сбрасываются
    в `false` при загрузке нового тайлсета). UI — в категории «Tiles Debug»: LOD-ползунок сверху,
    Freeze Camera + FOV и Pause Loading находятся сразу под Tile Bounds и доступны
    независимо от включения контуров. HUD дописывает маркеры `FROZEN`/`PAUSED`, когда
    сам HUD включён; ViewCube остаётся видимым при активном Freeze даже без Tile Bounds.
    Переводы en/ru/zh.
  - Тесты `tests/tiles.spec.ts` (DISCRETE_LOD): «заморозка… фиксирует отбор» (подлёт вплотную
    на заморозке не меняет `maxSelectedDepth`, разморозка — углубляет) и «пауза загрузки»
    (на паузе `queued>0`, `loading=0`, прогресса нет; снятие паузы дренит очередь до
    `queued=0`) и «ползунок LOD изолирует уровень»
    (изоляция 0 → `maxSelectedDepth=0`/`selected=1`, изоляция 1 → ровно уровень 1, снятие → полная).
- **Фаза 3 — ЧАСТИЧНО:** клик по тайлу сделан; остались нумерация блоков в порядке загрузки
  и луч приоритета near→far. Отдельный PiP-рендер не нужен: inspector работает в основном
  viewport.
  - `TileManager` ведёт `WeakMap<MeshInstance, Tile>`, наполняемую при подключении контента
    и очищаемую при выгрузке. `Viewer.pickDebugTileAt` делает точный raycast треугольников
    видимых тайлов и передаёт найденный меш менеджеру.
  - Режим `debug.tilePick` включается кнопкой «Выбрать тайл», взаимоисключается с измерениями,
    POI и выбором текстур. Перетаскивание камеры не считается кликом (порог 5 px).
    Под ним доступен `debug.tileIsolatePick`: после выбора остаётся виден только контент
    выбранного тайла; выключение сразу восстанавливает текущий LOD-срез. Если включить
    изоляцию до клика, обычная сцена остаётся видимой до первого выбора.
  - Выбранный тайл рисуется усиленным белым OBB. HUD показывает URL, LOD, state/refine,
    SSE, geometric error, distance, число контентов, байты и приблизительное число
    треугольников. Данные доступны из консоли через `viewer.getPickedTileInfo()`.

## Грабли окружения (иначе новая сессия выяснит заново)

- **In-app браузер подвешивает `requestAnimationFrame`** (у вьюера `autoRender === false`):

- **AppleDouble-мусор ломает git**: на внешнем томе macOS плодит `._*`, в т.ч. рядом с
  pack-файлами в `.git/` → ошибки «non-monotonic index» и неверный статус. Лечится

## Пункт 5 — поверхностная заливка отключена; клик сделан

Пользователь хочет видеть, как модель «состоит из кубиков», **прямо на поверхности**, и
**кликом по поверхности красить соответствующий тайл** (инструмент контроля). Bounding-боксы
для ближнего инспекта непригодны (крупнее геометрии, «висят в воздухе»).

**Подход подтверждён документацией CesiumJS:** `debugColorizeTiles` назначает цвет каждому
тайлу, чтобы видеть принадлежность features к тайлам. В PlayCanvas был проверен аналог через
клоны мешей в World-слое с полупрозрачным тёмным материалом, но визуально заливка не сработала;
экспериментальный код полностью удалён. Пока остаются толстые OBB-контуры.
- По отдельному переключателю доступна **слабая шахматная заливка самих OBB**. Это не
  поверхностная раскраска геометрии и по умолчанию выключено; инструмент оставлен как
  дополнительный обзорный режим, а не как основной способ инспекции вблизи.
- **Клик → тайл сделан** отдельным режимом `debug.tilePick`: точный CPU-raycast по
  треугольникам возвращает `MeshInstance`, обратная `WeakMap` менеджера находит владельца-
  тайл. Обычный `src/picker.ts` возвращает мировую точку глубины, а не `MeshInstance`, поэтому
  для этой задачи он не использован. Инструмент не ломает обычный выбор/измерения/POI:
  режимы взаимоисключающие.

## Грабли, на которые уже наступили (не повторять)

- **Заливка bounding-боксов не годится**: аддитивная — мутный туман; сплошная с записью
  глубины — заливала кадр и **пропадала изнутри бокса** (`CULLFACE_BACK`), даже `CULLFACE_NONE`
  не спас над геометрией. Пользователь просил заливку убрать → убрали. Не возвращать заливку
  объёма как основной механизм — идти в поверхностную раскраску геометрии (пункт 5).
- **Толстые линии**: нативной толщины у GL/WebGPU-линий нет → рисуем ленты-quad’ы, повёрнутые
  к камере (`obbEdgesThick`). Ширина регулируется ползунком «Толщина линий»; значение `2`
  соответствует прежней константе `0.002`.
- **Изоляция ≠ зажим глубины**: показывать ТОЛЬКО выбранный уровень, а не «всё вплоть до».
  И не форсировать загрузку всего уровня — уточнять по SSE, но не глубже (иначе на большой
  сцене тянет весь уровень).
