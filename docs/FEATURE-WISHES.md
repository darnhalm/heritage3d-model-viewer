# Пожелания по новым функциям

Документ для накопления идей и пожеланий по новым возможностям Model Viewer. Сюда можно дописывать пункты по мере появления.

## Список пожеланий

### Регрессия режима материалов `By objects / По объектам`

**Статус:** исправлено. При выключении режима выбор объекта очищается, а при
загрузке новой модели сбрасываются и runtime-ссылка на узел, и observer-состояние.

**Проблема:** перестал работать просмотр каналов и параметров материала отдельно для выбранного объекта при включённом режиме `By objects / По объектам` в разделе `Материалы`.

**При доработке проверить:**
- включение и выключение `debug.withTextureOnly`;
- выбор объекта кликом во viewport и обновление `scene.selectedNode`;
- фильтрацию mesh instances и материалов выбранного узла;
- переключение Base Color, Metalness, Roughness, Normal Map, Specular, Emissive, Lighting, AO и Opacity;
- появление и работу редакторов PBR-факторов и цветов выбранного материала;
- снятие выделения, смену объекта и возврат к общему просмотру;
- GLB/GLTF с одним и несколькими mesh/material, а также повторный вход во вкладку после загрузки новой модели;
- отсутствие регрессии от PCUI-обёрток и сохранение актуальных обработчиков при повторных нажатиях.

Добавить smoke-тест, который включает `By objects`, выбирает реальный узел модели, проверяет отдельный канал материала, меняет PBR-фактор и подтверждает, что изменение относится только к выбранному объекту.

### Усиление безопасности viewer и embed API

**Статус origin-hardening:** сделано для `embed=1`. Входящие команды принимаются только от прямого родителя с `parentOrigin` или origin из referrer; исходящие события и ответы отправляются на конкретный origin. Standalone-режим не изменён. Оставшиеся пункты этого раздела относятся к CSP, ресурсным лимитам и дальнейшему сокращению permissions.

**Описание:** Зафиксировать набор security-hardening задач для публичного viewer, особенно при использовании в iframe/embed-режиме и при загрузке моделей из внешних URL.

**Текущая оценка:** viewer выглядит приемлемо безопасным для обычного публичного просмотра моделей, но не является полностью hardened-решением для недоверенного окружения. Основные риски связаны не с XSS в UI, а с внешними URL, `postMessage`, iframe permissions и ресурсными лимитами.

**Контекст:**
- В `postMessage` API сейчас команды принимаются без проверки `event.origin`, а события наружу отправляются через `'*'`.
- Через `?load=` можно загружать модели по URL. Недоверенная модель может быть слишком большой, вызвать зависание вкладки, перерасход памяти GPU/браузера или задеть баги декодеров/WebGL/WebGPU.
- В проекте не зафиксирована строгая Content Security Policy для продакшен-деплоя.
- Сгенерированный iframe использует достаточно широкий набор permissions (`autoplay`, `fullscreen`, `xr-spatial-tracking`, `web-share`), который лучше минимизировать под конкретный сценарий.
- Viewer доступен как `window.viewer`, поэтому любые сторонние скрипты на той же странице могут управлять им.
- Важный плюс текущей реализации: UI в основном рендерится через React без явного `innerHTML`, а загрузка settings уже фильтрует опасные ключи `__proto__`, `constructor`, `prototype`.

**Желательно при доработке:**
- добавить allowlist origin для входящих `postMessage` команд;
- заменить `window.parent.postMessage(..., '*')` на конкретный `targetOrigin`;
- предусмотреть query-параметр или настройку embed вроде `parentOrigin`, чтобы внешний сайт явно указывал разрешённый origin;
- добавить лимиты на загружаемые модели: максимальный размер файла, количество мешей/примитивов, размер текстур, общий бюджет памяти;
- добавить таймауты загрузки и понятное сообщение об ошибке при превышении лимитов;
- продумать режим загрузки недоверенных моделей с отключённым WebGPU, если WebGPU не нужен;
- добавить рекомендации по CSP для сервера (`script-src`, `connect-src`, `img-src`, `worker-src`, `frame-ancestors`);
- минимизировать iframe permissions в embed-коде и включать `xr-spatial-tracking` / `web-share` только когда это действительно нужно;
- при необходимости ограничить или обернуть публичный `window.viewer` API, чтобы сторонние скрипты на странице не получали лишних возможностей;
- добавить отдельный smoke/security тест на `postMessage`: команды от неразрешённого origin должны игнорироваться, а события должны уходить только в разрешённый `targetOrigin`.

### Иконки вместо переключателей «Показывать» в настройках шаринга

**Желательно при доработке:**
- заменить таким представлением текущие переключатели левой панели, autoplay, fullscreen, `POI`, тура, измерений, информации, информации о модели, controls, fit и reset;

- отдельно пересобрать вертикальную компоновку панели для мобильных экранов: основная задача — уменьшить её высоту и по возможности показывать ключевые настройки и действие копирования без длинной прокрутки;

- большое поле с iframe-кодом на мобильном сделать сворачиваемым или показывать в отдельном preview/dialog; основным действием оставить заметную кнопку `Скопировать`;

- не уменьшать touch-target кнопок ниже удобного размера ради экономии высоты: уплотнять интерфейс прежде всего сеткой, сокращением отступов и скрытием второстепенных деталей;
- показывать название и текущее состояние в tooltip, например `POI: показывать` / `POI: скрыто`;
- добавить локализованный `aria-label` и состояние `aria-pressed`, чтобы кнопки оставались доступными с клавиатуры и для screen reader;
- не полагаться только на цвет: выключенное состояние должно читаться именно по перечёркиванию, а активное — дополнительно по фону/рамке;
- оставить текстовыми полями параметры, которые не являются простыми флагами: тип embed, пресет, размеры и язык.

#### Вернуть ручной выбор графического устройства

**Описание:** В строке `Current Device / Текущее устройство` снова дать пользователю возможность вручную выбрать графический backend, сохранив нынешний автоматический выбор лучшего доступного варианта по умолчанию.

**Предлагаемые варианты:**
- `Auto (recommended)` — сначала пробовать WebGPU и автоматически переходить на WebGL 2, если WebGPU недоступен или не запускается;
- `WebGPU` — явный пользовательский выбор с fallback и понятным сообщением при ошибке;
- `WebGL 2` — принудительный совместимый режим для диагностики, обхода драйверных проблем и сравнения рендера.

**Желательно при доработке:**
- заменить простую read-only строку текущего устройства на компактный selector или segmented control, рядом отдельно показывать фактически запущенный backend;
- помечать автоматически рекомендуемый вариант и по умолчанию оставлять `Auto`;
- недоступный вариант блокировать с tooltip, объясняющим причину;
- явно сообщать, что смена backend требует перезапуска графического устройства/перезагрузки viewer;
- при переключении сохранить текущую модель и пользовательские настройки, затем безопасно переоткрыть сцену в выбранном режиме;
- если принудительно выбранный backend не запустился, предложить либо автоматически выполнить fallback, либо вернуться в `Auto`, не оставляя viewer на пустом экране;
- ручной выбор хранить как локальную настройку браузера или параметр URL (`?webgl` / `?webgpu`), но не записывать его в settings JSON модели: backend зависит от устройства пользователя, а не от сцены;
- добавить действие `Вернуть Auto`, чтобы легко снять сохранённый ручной override.

### Подхват файла настроек при одновременном перетаскивании с моделью

**Статус:** отложено на потом.

**Описание:** Если пользователь перетаскивает в окно и модель, и файл настроек (`*.model-viewer-settings.json`) вместе (с тем же базовым именем, что и модель, или любой такой файл), автоматически читать содержимое файла настроек и применять его после загрузки модели, не показывая файл настроек в списке сцены.

**Контекст:** Реализация вызывала зависание лоадера (прогресс-бар останавливался примерно в середине), поэтому поддержка перетаскивания модели и настроек вместе отключена. Автоподхват настроек **из папки модели по URL** (когда модель открыта по ссылке и рядом лежит файл с тем же именем) работает.

**Желательно при доработке:** обеспечить стабильную загрузку без зависаний при перетаскивании модели и файла настроек вместе (таймауты, исключение файла настроек из списка ресурсов лоадера и т.п.).

### Цветокоррекция и кастомный LUT для сплатов

**Описание:** Добавить возможность применять кастомный LUT (Look-Up Table) для цветокоррекции Gaussian Splatting-моделей. Сейчас tonemap реализован аналитическими формулами (ACES, Filmic, Hejl и т.д.) в шейдере; LUT даёт более гибкий контроль и кинематографический вид.

**Контекст:** Готовых библиотек под PlayCanvas нет. Можно адаптировать логику из `glsl-lut` (npm) — GLSL-функция для 2D LUT 512×512, framework-agnostic. LUT практически не утяжеляет рендер (одна texture fetch на пиксель). Нужен post-process pass с full-screen quad и UI для выбора/загрузки текстуры LUT.

### Поведение параметра `?load=` при разных сценариях развёртывания

**Описание:** Сейчас значение `?load=` приводится к абсолютному URL (`new URL(loadUrl, window.location.href).href`) перед загрузкой модели. Решить в будущем, как обрабатывать относительные пути и сценарии развёртывания.

**Контекст:**
- При деплое в подпуть (например, `/viewer/`) путь `?load=/models/scull.glb` превращается в `http://site.com/models/scull.glb`, а не `http://site.com/viewer/models/scull.glb`. Если модели лежат относительно приложения, загрузка может не сработать.
- Если появится загрузка модели из файла конфигурации (URL в JSON), нужно определить: пути относительно origin, относительно приложения (base href) или относительно самого конфиг-файла.
- Текущая конвертация не затрагивает `model-viewer-settings.json` и `localStorage` — они используют отдельный код.

### Контурные аннотации и зоны на поверхности модели

**Описание:** Добавить инструмент аннотаций на поверхности модели не только в виде одиночных `POI`, но и в виде контуров/зон. Базовый сценарий: пользователь ставит несколько точек на поверхности, а viewer соединяет их линией или сглаженной кривой, привязанной к модели.

**Контекст:**
- Для задач реставрации, фиксации повреждений и визуального анализа часто нужна не отдельная точка, а область: трещина, скол, загрязнение, участок реставрации, граница интересующей зоны.
- Полноценная “Bezier-кривая на поверхности” или залитая область на меше — заметно более сложная задача, чем `POI`. Реалистичный первый этап — surface-anchored path: набор точек, поставленных raycast’ом на поверхность, соединённых линией или сглаженным контуром.
- В двухмерном плеере уже есть редактор SVG-контуров с опорными точками, симметричными ручками Bezier, выделением, удалением и перетаскиванием. Его UX и экранный слой управляющих элементов можно использовать как основу, но SVG path с координатами `x/y` не подходит как канонический формат настоящей 3D-аннотации.
- Для 3D-кривой нужны опорные точки и ручки в координатах `x/y/z`. Желательно хранить их в локальной системе модели, чтобы выравнивание, масштабирование и другие трансформации сцены не требовали вручную пересчитывать все аннотации.
- Обычная пространственная Bezier-кривая между точками поверхности может проходить сквозь модель или висеть над ней. Более точное прилегание потребует плотной дискретизации кривой и повторной проекции образцов на меш либо отдельного геодезического алгоритма.
- Для GLB возможна устойчивая привязка к мешу через triangle index и barycentric coordinates. Для Gaussian Splatting нет треугольной топологии, поэтому доступна только приблизительная, потенциально зависящая от камеры depth-привязка.
- Дальнейшее развитие может включать:
  - незамкнутые paths,
  - замкнутые контуры,
  - полупрозрачные залитые области на поверхности,
  - редактирование контрольных точек по аналогии с `POI`.

**Желательно при доработке:**
- начать с GLB-only MVP в виде surface path / closed contour без заливки;
- использовать тот же подход surface anchoring, что и у `POI` и измерений (`raycast + point + normal`);
- хранить аннотации в settings JSON как отдельную сущность (например, `annotations`) с 3D-опорными точками, входящими/исходящими ручками и нормалями;
- предусмотреть цвет, толщину, название, открытый/замкнутый тип и привязку к `POI`;
- редактировать ручки в экранном SVG-слое, проецируя 3D-точки через камеру, а саму кривую рисовать в 3D с depth test и небольшим отступом по нормали против z-fighting;
- ручки Bezier по возможности ограничивать локальной касательной плоскостью поверхности;
- поддержку сплатов проектировать отдельно как приблизительный режим и не обещать для них точный поверхностный контур;
- только после этого рассматривать более сложную задачу заливки области на поверхности.

### Изолированный просмотр блоков и срезы тайловой GLB-модели

**Статус:** первый production-этап реализован — точный настраиваемый OBB clipping box в нижней панели. Шесть плоскостей режут геометрию на GPU независимо от границ тайлов; доступны перемещение, размер, поворот, числовые параметры, инверсия и сброс по границам модели. Тайловый runtime дополнительно не запрашивает ветви, которые заведомо не пересекают оставляемый объём. Быстрый выбор области по тайлу, отдельные плоскости Section и section caps остаются будущими этапами.

**Описание:** Добавить в нижнюю панель viewer новый пользовательский инструмент для тайлового GLB-режима: изоляция выбранного фрагмента модели и просмотр крупной сцены по горизонтальным, вертикальным и произвольным срезам. Инструмент нужен для сцен, где внешняя оболочка здания мешает изучать интерьеры из обычного орбитального ракурса и общего масштаба.

**Основные сценарии:**
- кликнуть по видимому тайлу и временно оставить только соответствующий блок модели;
- обвести интересующую часть сцены изменяемым 3D-боксом и скрыть геометрию за его пределами;
- двигать горизонтальную плоскость как поэтажный срез сверху/снизу;
- двигать вертикальную плоскость для продольного или поперечного разреза здания;
- комбинировать несколько плоскостей либо грани бокса, чтобы получить ограниченный объём и свободно осматривать его изнутри;
- одним действием снять изоляцию и восстановить полную модель и исходный ракурс.

**Отличие от текущего Tiles Debug:**
- существующий `Isolate Picked Tile` является сессионным отладочным режимом и оставляет конкретный выбранный тайл текущего LOD;
- новый инструмент должен быть понятным production-инструментом исследования модели в нижней панели, без необходимости открывать `Materials → Tiles Debug`;
- изоляция должна задавать пространственную область или subtree, но внутри неё сохранять обычный streaming и уточнение LOD при приближении камеры, а не фиксировать качество исходного тайла.

**Предлагаемые режимы:**
1. `Tile` — выбор одного тайла или логической ветки тайлсета кликом, с возможностью добавлять и исключать блоки из набора.
2. `Box` — интерактивный AABB/OBB с ручками перемещения, размера и при необходимости поворота; показывается только содержимое внутри бокса.
3. `Section` — одна или несколько clipping planes с быстрыми ориентациями `Horizontal / Vertical X / Vertical Z` и возможностью инвертировать видимую сторону.

**Желательно при доработке:**
- показывать кнопку инструмента внизу только для совместимых тайловых GLB/3D Tiles-сцен; для обычного GLB поддержку можно добавить отдельно;
- при входе в режим сначала предлагать выбрать тайл либо нарисовать бокс по двум экранным точкам с последующей настройкой глубины;
- дать боксу и плоскостям простые 3D-гизмо, числовые поля позиции/размера и команды `Fit to selection`, `Reset`, `Invert`, `Hide outside/inside`;
- поддержать ортографическую камеру и быстрые виды сверху/спереди/сбоку для точной работы со срезами;
- после изоляции автоматически пересчитывать рамку навигации, pivot, скорость orbit/fly и camera clipping planes по видимой области, чтобы небольшой интерьер было удобно изучать;
- исключить скрытую clipping-геометрию из picking, `POI`, измерений и выделения объектов либо явно показать пользователю, если конкретный инструмент всё ещё работает по полной сцене;
- продолжать загружать нужные дочерние тайлы внутри выбранного объёма и по возможности не загружать заведомо отсечённые ветви тайлсета;
- корректно обрабатывать тайлы, пересекающие границу бокса: не скрывать весь тайл целиком, а применять GPU clipping к его геометрии;
- предусмотреть небольшой визуальный контур плоскости/бокса и понятное состояние активной изоляции, чтобы пользователь не принял неполную сцену за ошибку загрузки;
- учитывать, что обычный clipping открывает полые поверхности. Заполнение сечения (`section cap`) рассматривать отдельным этапом: для произвольной фотограмметрической сетки оно существенно сложнее простого скрытия фрагментов;
- по умолчанию считать изоляцию временным состоянием просмотра и не сохранять её в settings JSON; позже можно добавить именованные сохранённые срезы/ракурсы для презентаций и совместной работы;
- начать с WebGL/WebGPU-проверки одного clipping box и одной плоскости на GLB-тайлах, затем добавлять несколько плоскостей, наборы тайлов и сохранённые срезы.

### Общий прогресс и мгновенная пауза тура по POI — СДЕЛАНО

**Статус:** верхняя плашка показывает взвешенный общий прогресс. Pause
замораживает таймер, прогресс и перелёт камеры, Play продолжает с той же
фазы, Stop сбрасывает тур к первой обычной POI без доигрывания перелёта. Старые
таймеры защищены session token; хост получает `tour-state`. Точки-триггеры исключены из
тура, поэтому их внешнее аудио/анимация этим плеером не запускаются.

**Описание:** Улучшить верхний плеер тура: использовать фон плашки с названием текущей `POI` как единый индикатор общего прогресса тура, а команды паузы и остановки должны мгновенно замораживать всё воспроизведение, не ожидая завершения текущей карточки.

**Контекст:**
- Сейчас прогресс перехода и выдержки отображается отдельно внутри карточек `POI` в левой панели, но верхняя плашка тура не показывает, какая доля всего маршрута уже пройдена.
- Фон центральной части верхнего плеера можно постепенно заливать слева направо. Заполнение должно учитывать все карточки тура и фактические `duration + holdTime`, а не только номер текущей точки: карточки могут иметь разную длительность.
- Сейчас выключение `poi.playing` отменяет таймер автоматического перехода к следующей точке, однако уже запущенное движение камеры продолжает доигрываться. Из-за этого пауза воспринимается как отложенная.

**Желательно при доработке:**
- добавить фоновую заливку верхней плашки `POI` как общий progress bar всего тура;
- рассчитывать общий прогресс по сумме длительностей всех обычных `POI`, исключая точки-триггеры;
- различать уже завершённую часть тура и текущую карточку; при ручном переходе вперёд/назад сразу пересчитывать заполнение;
- по нажатию `Pause` немедленно остановить текущую интерполяцию камеры, таймер карточки, выдержку, связанное аудио и другие управляемые туром анимации;
- сохранять точную фазу и прошедшее время, чтобы `Play` мог продолжить с места паузы, а не перезапускать карточку;
- добавить явную команду `Stop`: мгновенно остановить те же процессы, сбросить прогресс и вернуть тур в начальное состояние;
- защититься от запоздалых callback старой карточки после паузы, остановки или ручного переключения (отмена активной анимации/таймера и проверка playback session token);
- синхронизировать состояние верхнего индикатора, карточек в левой панели и embed/postMessage-событий тура.

### Привязка внешней временно́й шкалы к кейфреймам анимации модели

**Описание:** Дать возможность внешней странице (через postMessage API) привязывать позицию на временно́й шкале к кейфреймам анимации модели — так, чтобы скролл шкалы или выбор события двигал анимацию вперёд/назад, а не только фокусировал камеру на POI.

**Контекст:**
- Сейчас embed API поддерживает только навигацию по POI (`focus-poi`, `next-poi`, `prev-poi`).
- Многие модели имеют встроенные анимации (например, реконструкция строительства, разрушения, реставрации). Логично синхронизировать временну́ю шкалу с прогрессом анимации.
- Типичный сценарий для хронотопа: на шкале есть события 1693–1990, каждое событие соответствует определённому кейфрейму анимации «жизни» объекта. При выборе события viewer переходит к нужному моменту анимации.
- Реализовать можно двумя способами:
  1. **По времени анимации** — внешняя страница отправляет `seek-animation { time: N }`, viewer ставит анимацию на нужную секунду;
  2. **По именованным маркерам** — в анимации расставляются именованные маркеры (аналог POI, но для временно́й оси), и внешняя страница переходит к ним по имени/id.

**Желательно при доработке:**
- добавить входящие postMessage команды:
  - `seek-animation { clip: string, time: number }` — прыжок к нужному времени;
  - `play-animation { clip: string, from?: number, to?: number }` — воспроизведение отрезка;
  - `pause-animation` — пауза;
- добавить исходящее событие `animation-time { clip, time, duration }` — чтобы внешняя шкала могла следить за прогрессом;
- по аналогии с POI добавить поддержку именованных «временных меток» анимации в settings JSON;
- предусмотреть `autoplay: false` при управлении снаружи, чтобы анимация не стартовала сама.

### Markdown-разметка в текстовых полях POI и информации

**Описание:** Дать возможность оформлять текст в описаниях `POI` и в информационных

  исполняется. Любой рендер Markdown снимает эту защиту, поэтому задача пересекается
  с разделом «Усиление безопасности viewer и embed API»: settings JSON может прийти
  из внешнего источника (`?load=`, автоподхват настроек рядом с моделью, импорт).

- Hover-label имеет фиксированную ширину 180px (`.poi-hover-label`), для списков и
  заголовков этого мало — потребуется отдельная типографика и, возможно, отдельный
  расширенный вид карточки точки.

**Желательно при доработке:**
- ограничиться безопасным подмножеством Markdown: `**bold**`, `*italic*`, списки,
  заголовки 2-3 уровня, ссылки, горизонтальный разделитель; без сырого HTML;
- рендерить через проверенный парсер с явным отключением HTML-блоков и последующей
  санитизацией результата, а не собственным `innerHTML` из регулярных выражений;
- у ссылок принудительно ставить `rel="noopener noreferrer"` и открывать во внешней
  вкладке; при необходимости ограничить схемы `http/https`;
- в редакторе описания оставить обычный текстовый ввод, но добавить предпросмотр или
  подсказку по поддерживаемому синтаксису;
- продумать деградацию: в узком hover-label показывать упрощённый вариант (без
  списков/заголовков), а полную разметку — в развёрнутой карточке или панели информации;
- решить, распространять ли Markdown на Dublin Core и вкладку `Information`, или
  ограничиться описаниями `POI` на первом этапе;
- добавить тест на то, что HTML и `javascript:`-ссылки из settings JSON не исполняются
  после включения Markdown.

### Иконки Material Symbols внутри нумерованных маркеров POI

**Описание:** Дать точкам интереса типы с разными иконками, сохранив при этом сквозную
нумерацию и порядок тура. Показывать в маркере одновременно иконку и номер.

**Ответ на вопрос о совместимости иконки и номера:** технически это возможно и не
требует отказа от нумерации. Маркер — обычный DOM-элемент `.poi-marker` (круг 28px,
`display: flex`), в который сейчас записывается только `textContent` с номером
(`src/viewer/controllers/poi-controller.ts:697`). Достаточно заменить текстовый узел на
два дочерних элемента. Рабочие варианты компоновки:
- **иконка в круге + номер бейджем** в правом верхнем/нижнем углу маркера — номер
  остаётся читаемым и не конкурирует с глифом за место в центре; предпочтительный вариант;
- **иконка сверху, номер под ней** внутри одного круга — требует увеличения маркера
  примерно до 34-36px и мелкого шрифта номера, на мобильных читается хуже;
- **иконка в круге, номер только в списке и в hover-label** — самый чистый вид, но
  порядок перестаёт читаться прямо во вьюпорте, поэтому как основной режим не подходит.

**Контекст:**
- Иконки Material Symbols подключаются одним `<link>` с **фиксированным списком**
  `icon_names=` в `src/index.html:51`. Глиф, не перечисленный в этом списке, отобразится
  как сырой текст — и в dev, и в проде. Значит, произвольный выбор любой иконки Google
  без изменения загрузки шрифта не заработает.
- Триггер-точки уже занимают центр маркера коротким системным именем (нота) или знаком
  `♪` и стилизуются классом `.poi-marker-trigger`. Новая схема должна с ними уживаться.
- Цвет маркера уже настраивается на точку (`poi.color`), контраст глифа и бейджа нужно
  проверять на светлых пользовательских цветах.

**Желательно при доработке:**
- ввести в модели `POI` поле типа/иконки и сохранять его в settings JSON, с безопасным
  дефолтом «без иконки» для старых файлов;
- предложить **курируемый набор** из примерно 20-40 иконок (например: информация,
  архитектура, скульптура, повреждение, реставрация, надпись, аудио, фото, документ,
  опасность), а не свободный ввод имени глифа;
- добавить выбранные имена в `icon_names=` в `src/index.html`; при желании дать
  свободный выбор — переходить на полный шрифт Material Symbols или динамическую
  подгрузку и явно оценить вес и офлайн-поведение;
- нумерацию сохранить как основной признак порядка: номер должен оставаться видимым во
  вьюпорте, в списке точек и в плеере тура;
- бейдж с номером сделать читаемым: контрастная подложка, обводка, минимальный размер
  шрифта, проверка на маркерах со светлым `poi.color`;
- пересчитать зону попадания (`POI_MARKER_HIT_RADIUS`) и touch-target, если маркер
  вырастет;
- согласовать вид с триггер-точками: у них вместо номера короткое имя, поэтому нужна
  единая схема «главный символ + вспомогательная метка»;
- в `aria-label` маркера добавлять название типа точки вместе с номером;
- не полагаться только на иконку и цвет как на смысловой признак: тип точки должен
  дублироваться текстом в hover-label и в списке.

### Автоматическая геопривязка 3D-моделей к карте портала

**Описание:** При загрузке геопривязанной модели автоматически извлекать координаты из
3D Tiles и передавать их через Site API в карту портала. Yandex Maps должен получать
готовую точку WGS 84 без обязательного ручного ввода адреса. Для моделей без геопривязки
оставить однократный выбор точки кликом на карте.

**Контекст:**
- 3D Tiles может хранить положение как `boundingVolume.region`, ECEF-трансляцию в
  `root.transform` / накопленных tile transforms и смещение `RTC_CENTER` в `.b3dm`;
- текущий viewer рецентрирует ECEF-тайлсет для устойчивого рендера, но не возвращает
  исходные `longitude / latitude / height` наружу и не поддерживает
  `boundingVolume.region` как географический bounding volume;
- в черновике API портала уже предусмотрен `GET /site/v1/catalog/map`, но контракт
  геолокации объекта и цифрового двойника ещё нужно зафиксировать;
- адрес не должен быть источником положения: при необходимости его можно получать
  обратным геокодированием из координат.

**Желательно при доработке:**
- выполнять извлечение геопривязки на backend в processing pipeline при приёме модели,
  до рецентровки и публикации viewer-производной;
- поддержать источники `boundingVolume.region`, ECEF `transform`, `RTC_CENTER` и явный
  CRS из metadata; применять точное преобразование эллипсоида через PROJ/GDAL или
  эквивалентную проверенную библиотеку, а не эвристику viewer по длине вектора;
- хранить отдельно `objectLocation` — подтверждённое место культурного объекта — и
  `twinGeoreference` — технический anchor конкретной 3D-модели: место съёмки или
  координаты модели могут не совпадать с текущим местом объекта;
- использовать канонический API-контракт с координатами в порядке
  `[longitude, latitude]`, высотой отдельным полем и явными `crs`, `source`,
  `accuracyMeters`, `isApproximate` и статусом подтверждения;
- возвращать координаты и краткую карточку через `GET /site/v1/catalog/map`, а полную
  геолокацию — в карточке объекта и цифрового двойника;
- добавить endpoint/операцию для подтверждения и ручной коррекции точки на карте без
  обязательного ввода адреса; локальные GLB/PLY/SPZ/SOG не считать геопривязанными
  автоматически;
- передавать в Yandex Maps готовые WGS 84 координаты; обратное геокодирование использовать
  только для человекочитаемого адреса и с учётом условий лицензии на хранение результата;
- при необходимости добавить `georeference` в подписанный viewer manifest, если viewer
  должен показывать координаты выбранной точки, но не делать браузерный viewer главным
  источником данных для карты;
- добавить тестовые наборы: `region`, ECEF transform, `RTC_CENTER`, локальная модель без
  CRS, ошибочный/неизвестный CRS и модель, для которой положение было исправлено вручную;
- проверить пограничные случаи: порядок широты/долготы, радианы против градусов,
  эллипсоидальная высота, пересечение 180-го меридиана и недостоверная автоматическая
  геопривязка.

### Поверхностная опорная точка камеры и pivot-индикатор

**Статус:** первый этап реализован 25 августа 2026 года; поведение референса изучено по исходникам
`NASA-AMMOS/3DTilesRendererJS` на commit
[`870df8656c4d37a57a9eb798cfb326fe14f79f72`](https://github.com/NASA-AMMOS/3DTilesRendererJS/tree/870df8656c4d37a57a9eb798cfb326fe14f79f72).
В viewer добавлены один depth pick после drag-threshold, настоящий off-axis orbit,
DOM-индикатор, отмена устаревших async-результатов, приоритет инструментов и настройка
`camera.surfacePivot`. Двойной клик теперь выполняет плавный двухкратный zoom-to-point
за 0,25 с. GIS-пресет с переставленными кнопками и непрерывное уточнение pinch-target
в этот этап не входят.

**Описание:** При начале жеста управления камерой находить поверхность под указателем,
использовать найденную мировую точку как временный центр вращения и показывать на ней
небольшой экранный кружок. Индикатор должен давать пользователю однозначную обратную
связь: вокруг какой точки сейчас вращается камера. Постоянный raycast при обычном
движении указателя для этой функции не нужен.

**Назначение:**
- сделать вращение крупных GLB и 3D Tiles предсказуемым, особенно при работе с
  внецентровыми деталями модели;
- визуально связать жест камеры с выбранной опорной точкой;
- использовать тот же механизм для будущих измерений, POI, clipping box и выбора
  геопривязочных контрольных точек, не дублируя picking в каждом инструменте;
- сохранить производительность тяжёлых сцен: один surface pick на жест вместо
  непрерывного перебора геометрии.

**Не является частью задачи:**
- индикатор не защищает GLB/тайлы от скачивания и не влияет на модель угроз viewer;
- сам по себе pivot не создаёт WGS 84-геопривязку;
- для белого pivot-кружка не нужна нормаль поверхности, номер треугольника или сырой URL
  тайла;
- постоянный «курсор поверхности» при hover и розовый debug-raycast рассматриваются как
  отдельные функции.

#### Что именно реализовано в референсе NASA

В примере существуют **два разных механизма**, которые нельзя смешивать:

1. **Белый `PivotPointMesh` в `EnvironmentControls`.** Это индикатор опорной точки
   управления камерой. Он появляется только во время активного жеста, использует одну
   найденную точку и не ориентируется по нормали поверхности.
2. **Розовый `rayIntersect` в debug-примере.** Это тор с коротким цилиндром, который
   ориентируется по нормали. При включённой настройке `raycast` он может пересчитываться
   каждый кадр. По умолчанию настройка выключена (`NONE`). Этот debug-инструмент не
   является pivot-индикатором камеры.

Исходники референса:
- [`EnvironmentControls.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/three/renderer/controls/EnvironmentControls.js) — состояния и жесты камеры;
- [`PointerTracker.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/three/renderer/controls/PointerTracker.js) — мышь и multitouch;
- [`PivotPointMesh.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/three/renderer/controls/PivotPointMesh.js) — экранный кружок;
- [`example/three/index.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/example/three/index.js) — отдельный debug-raycast;
- [`TilesRenderer.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/three/renderer/tiles/TilesRenderer.js) и
  [`raycastTraverse.js`](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/three/renderer/tiles/raycastTraverse.js) — ускоренный обход дерева тайлов.

Репозиторий распространяется по Apache License 2.0, а не MIT. Алгоритм и shader можно
адаптировать с сохранением требуемых уведомлений и атрибуции, но Three.js-код не является
готовой drop-in-зависимостью для PlayCanvas.

#### Визуальное устройство белого индикатора NASA

`PivotPointMesh` — один прозрачный quad с shader-отрисовкой окружности:
- размер задан в экранных пикселях и не меняется при приближении камеры;
- базовый параметр `size` равен `15`, толщина линии — `2`;
- `depthTest = false`, `depthWrite = false`, `renderOrder = Infinity`, поэтому кружок
  виден поверх модели;
- world matrix содержит только перенос к pivot, а форма строится в clip space;
- индикатор не использует normal, не наклоняется по поверхности и не участвует в
  raycast;
- после завершения жеста mesh удаляется из сцены.

Для нашего viewer тот же результат можно получить двумя способами:
- DOM/SVG-кружок, позиция которого обновляется через `worldToScreen`; это проще и
  согласуется с существующими overlay измерений и POI;
- отдельный PlayCanvas quad с screen-space shader; нужен только если индикатор должен
  попадать в canvas capture или видео.

Предпочтительный первый этап — DOM/SVG: один элемент, `pointer-events: none`, без
участия в picking. Для touch диаметр рекомендуется увеличить примерно до 28–32 CSS px,
потому что 15 px почти полностью закрываются пальцем.

#### Полное desktop-поведение NASA

| Ввод | Результат | Surface raycast | Индикатор |
|---|---|---:|---|
| Правая кнопка по поверхности | `ROTATE` вокруг найденного pivot | Один при `pointerdown` | Показан до `pointerup` |
| Левая кнопка по поверхности | `DRAG`: перемещение камеры по плоскости через pivot | Один при `pointerdown` | Добавлен на pivot |
| `Shift + левая` | `ROTATE`, если режим flight не перехватил жест | Один | Показан |
| Flight mode + клавиша движения/Shift | `FREE_ROTATE` вокруг позиции камеры | Не требуется | Не используется |
| Колесо | Zoom в направлении точки под указателем | Может уточняться во время zoom | Не используется |
| Двойной клик | Плавный zoom к выбранной поверхности | Один при подтверждённом double tap/click | Постоянно не показывается |
| Клик мимо геометрии | Fallback plane или отсутствие действия | Один промах | Не показывается |
| `pointerup` / `pointerleave` | Сброс состояния | Нет | Удаляется |

В конкретном `example/three/index.js` установлено `useFallbackPlane = false`, поэтому
правый drag по пустому фону не начинает surface rotation. Это поведение не следует
переносить автоматически: в универсальном model viewer пользователь должен иметь
возможность вращать камеру и после промаха, используя прежний focus.

После успешного `pointerdown` повторного raycast по геометрии для `ROTATE` нет.
`pointermove` меняет transform камеры вокруг сохранённой точки. Для `DRAG` используется
дешёвое пересечение луча с математической плоскостью через pivot, а не повторный обход
треугольников.

#### Полное mobile-поведение NASA

На touch-устройстве hover отсутствует, поэтому индикатор является не курсором, а
временной обратной связью активного жеста.

| Жест | Состояние и результат | Pivot-индикатор |
|---|---|---|
| Первый палец | Raycast в точке касания, `DRAG` относительно найденной поверхности | Pivot добавляется на найденную точку; видимость управляется состоянием touch-жеста |
| Второй палец | Raycast по центру между пальцами, переход в `WAITING` | Pivot переносится в точку под центром жеста |
| Пальцы расходятся/сходятся | `ZOOM`, если изменение расстояния между пальцами больше их параллельного смещения | Скрыт |
| Два пальца движутся параллельно | `ROTATE` вокруг pivot, если смещение центра преобладает над pinch | Показан |
| Один палец отпущен | Текущий multitouch-жест прекращается и состояние сбрасывается | Удаляется |
| Более двух пальцев | Жест отменяется | Удаляется |
| Двойной tap | Плавный zoom к найденной поверхности | Постоянно не показывается |

Порог выбора между `ZOOM` и `ROTATE` — примерно `2 × devicePixelRatio`. Двойной tap:
- интервал не более 300 мс;
- расстояние между tap не более `30 × devicePixelRatio`;
- смещение каждого tap не более `5 × devicePixelRatio`;
- стандартный коэффициент приближения — 2;
- стандартная длительность — около 0,25 с в актуальном исходнике.

Важное исключение производительности: во время pinch NASA может повторно уточнять
zoom-point raycast'ом, чтобы камера продолжала двигаться к поверхности между пальцами.
Это допустимо у них благодаря tile-aware обходу, но не должно копироваться буквально в
наш первый этап с текущим depth `Picker`.

#### Отличия текущего PlayCanvas viewer

Сейчас управление viewer отличается от NASA:
- левая кнопка вращает камеру;
- правая кнопка выполняет pan;
- один палец вращает;
- два пальца выполняют pan + pinch;
- `OrbitController` вращает вокруг центрального focus, заданного в `Pose`;
- двойной клик вызывает `Picker.pick(x, y)`, показывает ripple и меняет focus;
- `getPickableMeshInstances()` уже объединяет обычный GLB и mesh instances видимых
  тайлов;
- измерения и POI имеют собственные реализации точного raycast, что создаёт риск
  дублирования логики.

Просто показать кружок под указателем недостаточно: если камера продолжит вращаться
вокруг прежнего центрального focus, индикатор будет вводить пользователя в заблуждение.
Требуется реальное вращение camera transform вокруг произвольной мировой точки, в том
числе находящейся вне оптической оси.

Стандартный PlayCanvas `OrbitController` не хранит произвольный внецентровой pivot:
его focus всегда выводится из направления камеры и `Pose.distance`. Для поведения NASA
нужно на время жеста вращать позицию и orientation камеры вокруг world-space pivot, а
после `pointerup` синхронизировать результат обратно в `Pose`/`OrbitController`, чтобы
не было скачка в следующем кадре.

#### Рекомендуемая схема управления

Не менять существующие кнопки без отдельного UX-решения. Предусмотреть два пресета:

| Пресет | Левая кнопка | Правая кнопка | Mobile |
|---|---|---|---|
| `viewer` — рекомендуемый по умолчанию | Surface orbit + pivot-кружок | Pan | Один палец — surface orbit, два — pan/pinch |
| `gis` / `nasa` | Pan/выбор кликом | Surface orbit + pivot-кружок | Один палец — pan, два — rotate/pinch по логике GIS |

Короткий левый click должен по-прежнему работать для выбора объекта, POI и измерений.
Surface orbit активируется только после превышения click/drag threshold. Это сохраняет
совместимость инструментов и исключает лишний pick для обычного выбора.

Рекомендуемое mobile-поведение первого этапа:
- сохранить текущую привычную схему: один палец вращает, два пальца pan/pinch;
- после движения одного пальца дальше touch-slop выполнить один surface pick в
  исходной точке и начать orbit вокруг результата;
- показать увеличенный pivot-кружок вокруг пальца; на pinch скрыть его;
- при переходе ко второму пальцу зафиксировать один zoom/pan anchor в центре жеста,
  но не выполнять depth pick каждый кадр;
- двойной tap оставить для существующего центрирования;
- при отмене, `pointercancel`, потере capture и отпускании пальца всегда удалять marker;
- учитывать safe-area, `devicePixelRatio` и минимальный touch target, но сам overlay
  оставлять некликабельным.

#### Предлагаемая внутренняя архитектура

Добавить единый `SurfacePivotController` либо более общий `SurfacePickService`, который
обслуживает камеру и в будущем может использоваться измерениями/POI.

Минимальное состояние:

```ts
type SurfacePivotState =
    | { state: 'idle' }
    | { state: 'pending'; pointerId: number; requestId: number; start: [number, number] }
    | {
        state: 'active';
        pointerId: number;
        requestId: number;
        worldPoint: [number, number, number];
        sceneLocalPoint: [number, number, number];
        input: 'mouse' | 'touch' | 'pen';
    };
```

Жизненный цикл:

```text
pointerdown
  → ожидание click/drag threshold
  → один surface pick
  → проверка requestId и удержания pointer
  → active pivot + показать индикатор
  → вращение камеры без дополнительных surface picks
  → pointerup/cancel
  → синхронизация Pose + скрытие индикатора + idle
```

Обязательные правила:
- одновременно разрешён только один незавершённый pick;
- результат от старого `requestId` отбрасывается;
- результат от отпущенного pointer отбрасывается;
- при смене модели, сбросе сцены или закрытии viewer pending/active state отменяется;
- pivot хранится в стабильной системе координат корня сцены, а не как ссылка на
  треугольник текущего LOD: тайл может быть выгружен во время жеста;
- marker не должен попадать в picking и перехватывать pointer events;
- режимы `measure`, `poi`, `debug.tilePick`, `fragment.selecting`, gizmo/edit mode и
  fly mode должны иметь явный приоритет над surface orbit;
- при промахе использовать прежний camera focus и не показывать ложный marker;
- не публиковать наружу сырой URL тайла или внутренний индекс треугольника.

Внутренние события, если они понадобятся другим инструментам:

```ts
surfacePivotStart({
    worldPoint: [x, y, z],
    sceneLocalPoint: [x, y, z],
    input: 'mouse',
    controlScheme: 'viewer'
});

surfacePivotEnd({
    reason: 'pointerup' | 'cancel' | 'scene-reset' | 'miss'
});
```

Внешний `postMessage` API на первом этапе не требуется. Если портал должен получать
выбранную координату, добавить отдельное policy-controlled событие без tile URL и без
автоматической выдачи WGS 84. Географические координаты можно добавлять только при
наличии подтверждённого `twinGeoreference`.

#### Picking и производительность

Стоимость кружка и математики вращения пренебрежимо мала. Главный риск — определение
поверхности.

Текущий `src/picker.ts`:
- повторно рендерит слой `World` в pick target;
- читает один пиксель depth и восстанавливает world position;
- чтение `1×1` не означает рендер `1×1`: дорогой частью остаётся дополнительный проход
  всей видимой сцены;
- подходит для одного запроса по жесту, но не для `pointermove` или непрерывного pinch.

Текущий `src/viewer/controllers/mesh-raycast.ts`:
- возвращает точную point/normal;
- сначала фильтрует mesh instances по AABB;
- затем перебирает треугольники подходящего mesh;
- уже зафиксирован случай около миллиона треугольников с задержкой порядка секунды и
  блокировкой main thread;
- не должен использоваться на hover или touchmove без BVH/другого ускорения.

Первый этап:
- только world point из depth Picker;
- один pick после превышения drag threshold;
- normal не вычислять;
- не более одного запроса in flight;
- после получения pivot не выполнять дополнительные surface picks до завершения жеста.

Следующие оптимизации, если измерения покажут задержку на мобильных:
1. читать глубину уже сформированного кадра вместо повторного `World` pass;
2. использовать небольшой scissor/off-axis pick pass;
3. добавить tile-aware nearest-first обход bounding volumes;
4. построить BVH для монолитных GLB и отдельных tile meshes, желательно вне main thread;
5. использовать GPU object/normal pass только если инструментам действительно нужны
   mesh identity и normal.

Не копировать непрерывное уточнение pinch-target из NASA до появления дешёвого доступа
к depth или BVH. В нашей первой версии центр pinch фиксируется на начало жеста.

Целевые критерии производительности, которые следует проверить на реальных устройствах:
- в `idle` нет дополнительных pick/render/update операций;
- после разрешения pivot steady-state FPS не хуже baseline более чем на 5%;
- индикатор создаётся один раз на жест, а не каждый кадр;
- нет CPU long task от полного перебора тяжёлого GLB;
- p95 времени получения pivot: ориентир до 100 мс на desktop и до 150 мс на mobile;
- при более долгом pending камера не должна прыгать после отпускания пальца;
- тестировать WebGL2 и WebGPU отдельно, потому что readback ведёт себя по-разному.

Замер на Apple M1 / ANGLE Metal, Chromium, окно 1000×700, три baseline-прогона и пять
прогонов после реализации (`npm run benchmark:navigation`):

| Backend | p95 кадра до | p95 кадра после | Изменение | Pick p50 / p95 | Picks на drag |
|---|---:|---:|---:|---:|---:|
| WebGPU | 11,2 мс | 11,2 мс | 0% | 7,6 / 9,1 мс | 1 |
| WebGL2 | 11,3 мс | 11,7 мс | +3,5% | 21,5 / 23,9 мс | 1 |

WebGPU остался на baseline, WebGL2 уложился в установленный допуск 5%. CPU-часть
render p95 изменилась с 0,8 до 0,7 мс в WebGPU и с 0,8 до 0,6 мс в WebGL2; long task
не зафиксирован ни в одном из десяти финальных жестов.
Benchmark хранится отдельно от smoke-тестов, чтобы программный SwiftShader в CI не
выдавался за производительность реального GPU.

#### Примеры пользовательских сценариев

**Desktop, текущий пресет `viewer`:**
1. Пользователь ставит левую кнопку на плечо статуи.
2. После движения дальше click threshold viewer один раз определяет точку поверхности.
3. На плече появляется белый кружок.
4. Камера вращается вокруг плеча, а кружок остаётся визуально привязан к нему.
5. После отпускания кнопки кружок исчезает; следующий обычный click всё ещё может
   выбрать объект.

**Desktop, промах по фону:**
1. Пользователь начинает drag по пустой области.
2. Pick возвращает `null`.
3. Viewer продолжает использовать прежний центральный focus либо не начинает surface
   orbit согласно выбранной политике.
4. Индикатор не показывается.

**Mobile, один палец:**
1. Короткий tap не запускает surface orbit и остаётся доступным выбору/POI.
2. После движения дальше touch-slop выполняется один pick в исходной точке.
3. Появляется увеличенное кольцо, видимое вокруг пальца.
4. Камера вращается вокруг найденной детали без новых depth запросов.
5. `pointerup` немедленно скрывает кольцо.

**Mobile, переход к pinch:**
1. Пользователь добавляет второй палец.
2. Активный one-finger pivot завершается или преобразуется в multitouch anchor.
3. Кольцо скрывается.
4. Pan/pinch используют сохранённый центр между пальцами без surface pick на каждом
   событии движения.

**Запоздалый async-результат:**
1. Пользователь быстро коснулся тяжёлой сцены и отпустил палец.
2. GPU readback завершился после `pointerup`.
3. `requestId` уже неактуален, поэтому результат игнорируется.
4. Камера и marker не меняются с задержкой.

**3D Tiles и смена LOD:**
1. Pivot найден на mesh текущего тайла.
2. Во время вращения LOD заменяет этот tile другим.
3. Камера продолжает использовать сохранённую точку в scene-local/world coordinates,
   а не ссылку на выгруженный mesh.
4. Жест не прерывается и не меняет центр самопроизвольно.

#### Критерии приёмки

- Индикатор обозначает реальную точку вращения, а не декоративную позицию курсора.
- Размер индикатора визуально постоянен при любом zoom и DPR.
- Кружок не участвует в depth/pick и не перехватывает ввод.
- Off-axis pivot не вызывает скачка камеры при начале и окончании жеста.
- На обычном GLB и видимых GLB-тайлах используется один и тот же UX.
- Смена LOD или выгрузка исходного тайла не ломает активный жест.
- Tap/click, selection, измерения, POI, fragment box и gizmo не конфликтуют с orbit.
- `pointerup`, `pointercancel`, `pointerleave`, потеря capture, смена модели и выключение
  controls гарантированно очищают marker и pending request.
- Mobile pinch не запускает непрерывный полный render pass для depth picking.
- Double click/tap продолжает выполнять существующее центрирование.
- В fly mode предусмотрено понятное поведение без ложного surface pivot.
- Поведение проверено в WebGL2/WebGPU, desktop mouse, touch и pen.

#### План тестирования

**Unit:**
- вращение camera transform вокруг произвольного pivot;
- сохранение положения pivot в camera-local projection;
- синхронизация результата обратно в `Pose` без скачка;
- state machine `idle → pending → active → idle`;
- отмена stale `requestId` и результата после `pointerup`;
- выбор control preset и приоритет инструментов.

**Playwright/smoke:**
- GLB: click против drag, orbit вокруг внецентровой детали, промах по фону;
- 3D Tiles: pivot по видимому tile mesh, замена LOD во время жеста;
- mouse: левая/правая кнопка в обоих пресетах;
- mobile emulation: один палец, второй палец, pinch, double tap, cancel;
- измерения/POI/fragment: camera pivot не перехватывает инструмент;
- marker исчезает после каждого пути завершения;
- отсутствие повторных pick во время активного orbit;
- отдельный performance trace на тяжёлом GLB и тайлсете.

**Набор производительных сцен:**
- небольшой GLB;
- монолитный GLB около 1 млн треугольников;
- 3D Tiles с частой сменой LOD;
- сцена с большим количеством draw calls;
- мобильное устройство среднего/низкого класса или соответствующий throttling profile.

#### Этапы и предварительная оценка

1. **Визуальный прототип:** DOM/SVG marker и lifecycle без изменения камеры — около
   1 рабочего дня. Такой прототип нельзя считать готовой функцией, потому что marker
   ещё не доказывает реальный pivot.
2. **Desktop surface orbit:** один pick, произвольный world pivot, camera math и
   синхронизация `Pose` — ориентировочно 2–3 рабочих дня.
3. **Production-интеграция:** GLB/тайлы, async cancellation, режимы инструментов,
   control presets и автотесты — суммарно около 5–8 рабочих дней.
4. **Mobile и расширенные жесты:** touch state machine, pinch transition, damping,
   zoom-to-point и дополнительные тесты — ещё 3–5 рабочих дней.
5. **Оптимизация второго этапа:** reuse depth/BVH/tile-aware raycast — оценивать после
   профилирования и отдельно от базового pivot UX.
