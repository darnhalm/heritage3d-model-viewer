# Пожелания по новым функциям

Документ для накопления идей и пожеланий по новым возможностям Model Viewer. Сюда можно дописывать пункты по мере появления.

---

## Список пожеланий

### Усиление безопасности viewer и embed API

**Статус origin-hardening:** сделано для `embed=1`. Входящие команды принимаются только от прямого родителя с `parentOrigin` или origin из referrer; исходящие события и ответы отправляются на конкретный origin. Standalone-режим не изменён. Оставшиеся пункты этого раздела относятся к CSP, ресурсным лимитам и дальнейшему сокращению permissions.

**Описание:** Зафиксировать набор security-hardening задач для публичного viewer, особенно при использовании в iframe/embed-режиме и при загрузке моделей из внешних URL.

**Текущая оценка:** viewer выглядит приемлемо безопасным для обычного публичного просмотра моделей, но не является полностью hardened-решением для недоверенного окружения. Основные риски связаны не с XSS в UI, а с внешними URL, `postMessage`, iframe permissions и ресурсными лимитами.

**Контекст:**
- В `postMessage` API сейчас команды принимаются без проверки `event.origin`, а события наружу отправляются через `'*'`.
- Через `?load=` можно загружать модели по URL. Недоверенная модель может быть слишком большой, вызвать зависание вкладки, перерасход памяти GPU/браузера или задеть баги декодеров/WebGL/WebGPU.
- В проекте не зафиксирована строгая Content Security Policy для продакшен-деплоя.
- Сгенерированный iframe использует достаточно широкий набор permissions (`autoplay`, `fullscreen`, `xr-spatial-tracking`, `web-share`), который лучше минимизировать под конкретный сценарий.
- Viewer доступен как `window.viewer`, поэтому любые сторонние скрипты на той же странице могут управлять им.
- Важный плюс текущей реализации: UI в основном рендерится через React без явного `innerHTML`, а загрузка settings уже фильтрует опасные ключи `__proto__`, `constructor`, `prototype`.

**Желательно при доработке:**
- добавить allowlist origin для входящих `postMessage` команд;
- заменить `window.parent.postMessage(..., '*')` на конкретный `targetOrigin`;
- предусмотреть query-параметр или настройку embed вроде `parentOrigin`, чтобы внешний сайт явно указывал разрешённый origin;
- добавить лимиты на загружаемые модели: максимальный размер файла, количество мешей/примитивов, размер текстур, общий бюджет памяти;
- добавить таймауты загрузки и понятное сообщение об ошибке при превышении лимитов;
- продумать режим загрузки недоверенных моделей с отключённым WebGPU, если WebGPU не нужен;
- добавить рекомендации по CSP для сервера (`script-src`, `connect-src`, `img-src`, `worker-src`, `frame-ancestors`);
- минимизировать iframe permissions в embed-коде и включать `xr-spatial-tracking` / `web-share` только когда это действительно нужно;
- при необходимости ограничить или обернуть публичный `window.viewer` API, чтобы сторонние скрипты на странице не получали лишних возможностей;
- добавить отдельный smoke/security тест на `postMessage`: команды от неразрешённого origin должны игнорироваться, а события должны уходить только в разрешённый `targetOrigin`.

### Иконки вместо переключателей «Показывать» в настройках шаринга

**Описание:** Сделать настройки состава интерфейса в разделе `View & Share` / генераторе embed-кода более компактными и наглядными. Вместо длинного списка текстовых переключателей `Show ...` показывать ряд или сетку кнопок с иконками соответствующих функций.

**Предлагаемое поведение:**
- включённая функция отображается обычной активной иконкой;
- выключенная функция отображается той же иконкой с диагональным перечёркиванием;
- нажатие на иконку сразу переключает состояние и обновляет сгенерированные URL и iframe-код;
- состояния должны синхронно обновляться при выборе пресетов `Full / Compact / Minimal`.

**Желательно при доработке:**
- заменить таким представлением текущие переключатели левой панели, autoplay, fullscreen, `POI`, тура, измерений, информации, информации о модели, controls, fit и reset;
- сгруппировать иконки по смыслу и сохранить одинаковый размер активной области на desktop и touch-устройствах;
- отдельно пересобрать вертикальную компоновку панели для мобильных экранов: основная задача — уменьшить её высоту и по возможности показывать ключевые настройки и действие копирования без длинной прокрутки;
- флаги интерфейса расположить компактной адаптивной сеткой иконок в несколько колонок, а не отдельными строками на всю ширину;
- объединить связанные параметры в короткие строки, например `Embed type + Preset`, `Width × Height` и `Language`, если ширина экрана это позволяет;
- менее частые параметры размеров и расширенные настройки убирать под раскрываемый блок `Дополнительно`, особенно для responsive embed;
- большое поле с iframe-кодом на мобильном сделать сворачиваемым или показывать в отдельном preview/dialog; основным действием оставить заметную кнопку `Скопировать`;
- предусмотреть компактный режим панели при малой высоте viewport, учитывать safe-area и появление экранной клавиатуры;
- не уменьшать touch-target кнопок ниже удобного размера ради экономии высоты: уплотнять интерфейс прежде всего сеткой, сокращением отступов и скрытием второстепенных деталей;
- показывать название и текущее состояние в tooltip, например `POI: показывать` / `POI: скрыто`;
- добавить локализованный `aria-label` и состояние `aria-pressed`, чтобы кнопки оставались доступными с клавиатуры и для screen reader;
- не полагаться только на цвет: выключенное состояние должно читаться именно по перечёркиванию, а активное — дополнительно по фону/рамке;
- оставить текстовыми полями параметры, которые не являются простыми флагами: тип embed, пресет, размеры и язык.

### Перенос постоянного `TWIN_ID` в информацию о модели

**Описание:** Убрать отдельную кнопку `ID` из нижней панели viewer. Вместо отдельной панели идентификации показывать `TWIN_ID` во вкладке `Model` панели информации.

**Назначение `TWIN_ID`:** Постоянный глобально уникальный идентификатор цифрового двойника. Он связывает конкретный 3D-ресурс и его настройки во viewer с метаинформацией соответствующего объекта на сайте.

**Желательно при доработке:**
- удалить кнопку `#id-button` из нижней панели и не оставлять пустую отдельную ID-панель;
- добавить во вкладку `Information → Model` отдельную read-only строку `TWIN_ID` с кнопкой копирования;
- визуально отделить `TWIN_ID` от временных внутренних ID, имени файла, URL, пути узла и идентификаторов объектов сцены;
- не изменять и не генерировать новый `TWIN_ID` при переименовании файла, смене URL, повторной загрузке, экспорте/импорте настроек или обновлении версии модели;
- получать `TWIN_ID` из согласованного источника сайта/API и сохранять его в переносимом settings JSON; при отсутствии показывать понятное состояние `TWIN_ID не назначен`, а не случайный локальный идентификатор;
- использовать `TWIN_ID` как ключ связи с метаданными сайта, но не подменять им ID отдельных `POI`, узлов сцены, файлов и версий модели;
- определить миграцию полезных функций существующей ID-панели: Dublin Core оставить в информационном разделе, а путь выбранного узла и его копирование перенести в сведения о выбранном объекте либо удалить отдельно осознанным решением;
- проверить контракт именования с уже используемыми на стороне портала идентификаторами (`H3DID` / `h3druObjectId`): зафиксировать, является ли `TWIN_ID` отдельным ID цифрового двойника или новым названием существующего поля.

#### Вернуть ручной выбор графического устройства

**Описание:** В строке `Current Device / Текущее устройство` снова дать пользователю возможность вручную выбрать графический backend, сохранив нынешний автоматический выбор лучшего доступного варианта по умолчанию.

**Предлагаемые варианты:**
- `Auto (recommended)` — сначала пробовать WebGPU и автоматически переходить на WebGL 2, если WebGPU недоступен или не запускается;
- `WebGPU` — явный пользовательский выбор с fallback и понятным сообщением при ошибке;
- `WebGL 2` — принудительный совместимый режим для диагностики, обхода драйверных проблем и сравнения рендера.

**Желательно при доработке:**
- заменить простую read-only строку текущего устройства на компактный selector или segmented control, рядом отдельно показывать фактически запущенный backend;
- помечать автоматически рекомендуемый вариант и по умолчанию оставлять `Auto`;
- недоступный вариант блокировать с tooltip, объясняющим причину;
- явно сообщать, что смена backend требует перезапуска графического устройства/перезагрузки viewer;
- при переключении сохранить текущую модель и пользовательские настройки, затем безопасно переоткрыть сцену в выбранном режиме;
- если принудительно выбранный backend не запустился, предложить либо автоматически выполнить fallback, либо вернуться в `Auto`, не оставляя viewer на пустом экране;
- ручной выбор хранить как локальную настройку браузера или параметр URL (`?webgl` / `?webgpu`), но не записывать его в settings JSON модели: backend зависит от устройства пользователя, а не от сцены;
- добавить действие `Вернуть Auto`, чтобы легко снять сохранённый ручной override.

### Подхват файла настроек при одновременном перетаскивании с моделью

**Описание:** Если пользователь перетаскивает в окно и модель, и файл настроек (`*.model-viewer-settings.json`) вместе (с тем же базовым именем, что и модель, или любой такой файл), автоматически читать содержимое файла настроек и применять его после загрузки модели, не показывая файл настроек в списке сцены.

**Контекст:** Реализация вызывала зависание лоадера (прогресс-бар останавливался примерно в середине), поэтому поддержка перетаскивания модели и настроек вместе отключена. Автоподхват настроек **из папки модели по URL** (когда модель открыта по ссылке и рядом лежит файл с тем же именем) работает.

**Желательно при доработке:** обеспечить стабильную загрузку без зависаний при перетаскивании модели и файла настроек вместе (таймауты, исключение файла настроек из списка ресурсов лоадера и т.п.).

### Цветокоррекция и кастомный LUT для сплатов

**Описание:** Добавить возможность применять кастомный LUT (Look-Up Table) для цветокоррекции Gaussian Splatting-моделей. Сейчас tonemap реализован аналитическими формулами (ACES, Filmic, Hejl и т.д.) в шейдере; LUT даёт более гибкий контроль и кинематографический вид.

**Контекст:** Готовых библиотек под PlayCanvas нет. Можно адаптировать логику из `glsl-lut` (npm) — GLSL-функция для 2D LUT 512×512, framework-agnostic. LUT практически не утяжеляет рендер (одна texture fetch на пиксель). Нужен post-process pass с full-screen quad и UI для выбора/загрузки текстуры LUT.

### Поведение параметра `?load=` при разных сценариях развёртывания

**Описание:** Сейчас значение `?load=` приводится к абсолютному URL (`new URL(loadUrl, window.location.href).href`) перед загрузкой модели. Решить в будущем, как обрабатывать относительные пути и сценарии развёртывания.

**Контекст:**
- При деплое в подпуть (например, `/viewer/`) путь `?load=/models/scull.glb` превращается в `http://site.com/models/scull.glb`, а не `http://site.com/viewer/models/scull.glb`. Если модели лежат относительно приложения, загрузка может не сработать.
- Если появится загрузка модели из файла конфигурации (URL в JSON), нужно определить: пути относительно origin, относительно приложения (base href) или относительно самого конфиг-файла.
- Текущая конвертация не затрагивает `model-viewer-settings.json` и `localStorage` — они используют отдельный код.

**Желательно при доработке:** добавить учёт base href / базового URL приложения; при необходимости — сделать режим конвертации опциональным.

### Выбор качества текстур при загрузке модели

**Описание:** Добавить выбор качества текстур (`Auto / High / Medium / Low`) при загрузке модели, чтобы viewer мог открывать одну и ту же модель с разным разрешением текстур в зависимости от устройства или выбора пользователя.

**Контекст:**
- Сейчас, если модель приходит с `8K` текстурами, viewer загружает именно их. Обычные GPU mipmaps не решают задачу выбора качества загрузки: `8K` всё равно сначала скачивается и попадает в память.
- Полноценного runtime texture streaming / texture LOD, как у крупных платформ вроде Sketchfab, в проекте сейчас нет.
- Наиболее реалистичная реализация для этого viewer — не downscale уже загруженной текстуры, а подготовка нескольких наборов текстур заранее (`8K / 4K / 2K / 1K`) и выбор нужного набора в момент загрузки.
- Для `.gltf` это проще через подмену путей к текстурам. Для `.glb` практичнее либо хранить несколько отдельных версий модели, либо иметь preprocessing pipeline, который извлекает и готовит texture tiers заранее.

**Желательно при доработке:**
- добавить в UI `Texture Quality: Auto / High / Medium / Low`;
- реализовать выбор через заранее подготовленные texture sets, а не через runtime downscale;

### Контурные аннотации и зоны на поверхности модели

**Описание:** Добавить инструмент аннотаций на поверхности модели не только в виде одиночных `POI`, но и в виде контуров/зон. Базовый сценарий: пользователь ставит несколько точек на поверхности, а viewer соединяет их линией или сглаженной кривой, привязанной к модели.

**Контекст:**
- Для задач реставрации, фиксации повреждений и визуального анализа часто нужна не отдельная точка, а область: трещина, скол, загрязнение, участок реставрации, граница интересующей зоны.
- Полноценная “Bezier-кривая на поверхности” или залитая область на меше — заметно более сложная задача, чем `POI`. Реалистичный первый этап — surface-anchored path: набор точек, поставленных raycast’ом на поверхность, соединённых линией или сглаженным контуром.
- В двухмерном плеере уже есть редактор SVG-контуров с опорными точками, симметричными ручками Bezier, выделением, удалением и перетаскиванием. Его UX и экранный слой управляющих элементов можно использовать как основу, но SVG path с координатами `x/y` не подходит как канонический формат настоящей 3D-аннотации.
- Для 3D-кривой нужны опорные точки и ручки в координатах `x/y/z`. Желательно хранить их в локальной системе модели, чтобы выравнивание, масштабирование и другие трансформации сцены не требовали вручную пересчитывать все аннотации.
- Обычная пространственная Bezier-кривая между точками поверхности может проходить сквозь модель или висеть над ней. Более точное прилегание потребует плотной дискретизации кривой и повторной проекции образцов на меш либо отдельного геодезического алгоритма.
- Для GLB возможна устойчивая привязка к мешу через triangle index и barycentric coordinates. Для Gaussian Splatting нет треугольной топологии, поэтому доступна только приблизительная, потенциально зависящая от камеры depth-привязка.
- Дальнейшее развитие может включать:
  - незамкнутые paths,
  - замкнутые контуры,
  - полупрозрачные залитые области на поверхности,
  - редактирование контрольных точек по аналогии с `POI`.

**Желательно при доработке:**
- начать с GLB-only MVP в виде surface path / closed contour без заливки;
- использовать тот же подход surface anchoring, что и у `POI` и измерений (`raycast + point + normal`);
- хранить аннотации в settings JSON как отдельную сущность (например, `annotations`) с 3D-опорными точками, входящими/исходящими ручками и нормалями;
- предусмотреть цвет, толщину, название, открытый/замкнутый тип и привязку к `POI`;
- редактировать ручки в экранном SVG-слое, проецируя 3D-точки через камеру, а саму кривую рисовать в 3D с depth test и небольшим отступом по нормали против z-fighting;
- ручки Bezier по возможности ограничивать локальной касательной плоскостью поверхности;
- поддержку сплатов проектировать отдельно как приблизительный режим и не обещать для них точный поверхностный контур;
- только после этого рассматривать более сложную задачу заливки области на поверхности.

### Изолированный просмотр блоков и срезы тайловой GLB-модели

**Описание:** Добавить в нижнюю панель viewer новый пользовательский инструмент для тайлового GLB-режима: изоляция выбранного фрагмента модели и просмотр крупной сцены по горизонтальным, вертикальным и произвольным срезам. Инструмент нужен для сцен, где внешняя оболочка здания мешает изучать интерьеры из обычного орбитального ракурса и общего масштаба.

**Основные сценарии:**
- кликнуть по видимому тайлу и временно оставить только соответствующий блок модели;
- обвести интересующую часть сцены изменяемым 3D-боксом и скрыть геометрию за его пределами;
- двигать горизонтальную плоскость как поэтажный срез сверху/снизу;
- двигать вертикальную плоскость для продольного или поперечного разреза здания;
- комбинировать несколько плоскостей либо грани бокса, чтобы получить ограниченный объём и свободно осматривать его изнутри;
- одним действием снять изоляцию и восстановить полную модель и исходный ракурс.

**Отличие от текущего Tiles Debug:**
- существующий `Isolate Picked Tile` является сессионным отладочным режимом и оставляет конкретный выбранный тайл текущего LOD;
- новый инструмент должен быть понятным production-инструментом исследования модели в нижней панели, без необходимости открывать `Materials → Tiles Debug`;
- изоляция должна задавать пространственную область или subtree, но внутри неё сохранять обычный streaming и уточнение LOD при приближении камеры, а не фиксировать качество исходного тайла.

**Предлагаемые режимы:**
1. `Tile` — выбор одного тайла или логической ветки тайлсета кликом, с возможностью добавлять и исключать блоки из набора.
2. `Box` — интерактивный AABB/OBB с ручками перемещения, размера и при необходимости поворота; показывается только содержимое внутри бокса.
3. `Section` — одна или несколько clipping planes с быстрыми ориентациями `Horizontal / Vertical X / Vertical Z` и возможностью инвертировать видимую сторону.

**Желательно при доработке:**
- показывать кнопку инструмента внизу только для совместимых тайловых GLB/3D Tiles-сцен; для обычного GLB поддержку можно добавить отдельно;
- при входе в режим сначала предлагать выбрать тайл либо нарисовать бокс по двум экранным точкам с последующей настройкой глубины;
- дать боксу и плоскостям простые 3D-гизмо, числовые поля позиции/размера и команды `Fit to selection`, `Reset`, `Invert`, `Hide outside/inside`;
- поддержать ортографическую камеру и быстрые виды сверху/спереди/сбоку для точной работы со срезами;
- после изоляции автоматически пересчитывать рамку навигации, pivot, скорость orbit/fly и camera clipping planes по видимой области, чтобы небольшой интерьер было удобно изучать;
- исключить скрытую clipping-геометрию из picking, `POI`, измерений и выделения объектов либо явно показать пользователю, если конкретный инструмент всё ещё работает по полной сцене;
- продолжать загружать нужные дочерние тайлы внутри выбранного объёма и по возможности не загружать заведомо отсечённые ветви тайлсета;
- корректно обрабатывать тайлы, пересекающие границу бокса: не скрывать весь тайл целиком, а применять GPU clipping к его геометрии;
- предусмотреть небольшой визуальный контур плоскости/бокса и понятное состояние активной изоляции, чтобы пользователь не принял неполную сцену за ошибку загрузки;
- учитывать, что обычный clipping открывает полые поверхности. Заполнение сечения (`section cap`) рассматривать отдельным этапом: для произвольной фотограмметрической сетки оно существенно сложнее простого скрытия фрагментов;
- по умолчанию считать изоляцию временным состоянием просмотра и не сохранять её в settings JSON; позже можно добавить именованные сохранённые срезы/ракурсы для презентаций и совместной работы;
- начать с WebGL/WebGPU-проверки одного clipping box и одной плоскости на GLB-тайлах, затем добавлять несколько плоскостей, наборы тайлов и сохранённые срезы.

### Общий прогресс и мгновенная пауза тура по POI — СДЕЛАНО

**Статус:** верхняя плашка показывает взвешенный общий прогресс. Pause
замораживает таймер, прогресс и перелёт камеры, Play продолжает с той же
фазы, Stop сбрасывает тур к первой обычной POI без доигрывания перелёта. Старые
таймеры защищены session token; хост получает `tour-state`. Точки-триггеры исключены из
тура, поэтому их внешнее аудио/анимация этим плеером не запускаются.

**Описание:** Улучшить верхний плеер тура: использовать фон плашки с названием текущей `POI` как единый индикатор общего прогресса тура, а команды паузы и остановки должны мгновенно замораживать всё воспроизведение, не ожидая завершения текущей карточки.

**Контекст:**
- Сейчас прогресс перехода и выдержки отображается отдельно внутри карточек `POI` в левой панели, но верхняя плашка тура не показывает, какая доля всего маршрута уже пройдена.
- Фон центральной части верхнего плеера можно постепенно заливать слева направо. Заполнение должно учитывать все карточки тура и фактические `duration + holdTime`, а не только номер текущей точки: карточки могут иметь разную длительность.
- Сейчас выключение `poi.playing` отменяет таймер автоматического перехода к следующей точке, однако уже запущенное движение камеры продолжает доигрываться. Из-за этого пауза воспринимается как отложенная.

**Желательно при доработке:**
- добавить фоновую заливку верхней плашки `POI` как общий progress bar всего тура;
- рассчитывать общий прогресс по сумме длительностей всех обычных `POI`, исключая точки-триггеры;
- различать уже завершённую часть тура и текущую карточку; при ручном переходе вперёд/назад сразу пересчитывать заполнение;
- по нажатию `Pause` немедленно остановить текущую интерполяцию камеры, таймер карточки, выдержку, связанное аудио и другие управляемые туром анимации;
- сохранять точную фазу и прошедшее время, чтобы `Play` мог продолжить с места паузы, а не перезапускать карточку;
- добавить явную команду `Stop`: мгновенно остановить те же процессы, сбросить прогресс и вернуть тур в начальное состояние;
- защититься от запоздалых callback старой карточки после паузы, остановки или ручного переключения (отмена активной анимации/таймера и проверка playback session token);
- синхронизировать состояние верхнего индикатора, карточек в левой панели и embed/postMessage-событий тура.

### Привязка внешней временно́й шкалы к кейфреймам анимации модели

**Описание:** Дать возможность внешней странице (через postMessage API) привязывать позицию на временно́й шкале к кейфреймам анимации модели — так, чтобы скролл шкалы или выбор события двигал анимацию вперёд/назад, а не только фокусировал камеру на POI.

**Контекст:**
- Сейчас embed API поддерживает только навигацию по POI (`focus-poi`, `next-poi`, `prev-poi`).
- Многие модели имеют встроенные анимации (например, реконструкция строительства, разрушения, реставрации). Логично синхронизировать временну́ю шкалу с прогрессом анимации.
- Типичный сценарий для хронотопа: на шкале есть события 1693–1990, каждое событие соответствует определённому кейфрейму анимации «жизни» объекта. При выборе события viewer переходит к нужному моменту анимации.
- Реализовать можно двумя способами:
  1. **По времени анимации** — внешняя страница отправляет `seek-animation { time: N }`, viewer ставит анимацию на нужную секунду;
  2. **По именованным маркерам** — в анимации расставляются именованные маркеры (аналог POI, но для временно́й оси), и внешняя страница переходит к ним по имени/id.

**Желательно при доработке:**
- добавить входящие postMessage команды:
  - `seek-animation { clip: string, time: number }` — прыжок к нужному времени;
  - `play-animation { clip: string, from?: number, to?: number }` — воспроизведение отрезка;
  - `pause-animation` — пауза;
- добавить исходящее событие `animation-time { clip, time, duration }` — чтобы внешняя шкала могла следить за прогрессом;
- по аналогии с POI добавить поддержку именованных «временных меток» анимации в settings JSON;
- предусмотреть `autoplay: false` при управлении снаружи, чтобы анимация не стартовала сама.

*Ниже можно добавлять новые пожелания по одному в таком же формате (заголовок, описание, при необходимости контекст).*
